Container orchestration
in one binary.

Kanea runs your services on containerd, networks them with its own eBPF datapath, terminates TLS with Let's Encrypt, and ships a live dashboard, an MCP server, GitOps pipelines and encrypted S3 backups. One static binary, with no Kubernetes required — not underneath, not for the CNI, not for the load balancer. 

$ curl -fsSL https://m18h.github.io/kanea/install.sh | sudo bash

Piping a script into a root shell deserves a look first — read it first, or install it by hand. Every download is checksum-verified with no flag to skip it.

What it is

A control plane you can read in an afternoon

Three processes from one binary: kanead converges state, kanea-edge carries north–south traffic, and the CLI talks to both. The edge is deliberately not a child of the control plane — restarting kanead never drops a request in flight.

Runtime

containerd, hardened by default

Capabilities dropped to a reviewed uid-switching baseline (["none"] drops the rest), no-new-privileges, the default seccomp profile, per-alloc PID and IPC namespaces — and no privileged escape hatch in the spec at all. Nothing runs uncapped: workloads share a cgroup with a hard ceiling, and the control plane holds a kernel-guaranteed memory floor beneath it.

Network

First-party eBPF, no k8s

Connect-time service load balancing, per-project default-deny policy and per-alloc plumbing from three eBPF programs compiled into the binary — no network agent, no kvstore, no CNI. Services find each other over internal DNS, and the same maps supply the east-west metrics the autoscaler reads.

Edge

TLS that renews itself

ACME HTTP-01 out of the box and DNS-01 for wildcards, issued in the control plane and published to the edge. Per-route middleware — IP restriction, token-bucket rate limiting, header rewriting — evaluated in a fixed order.

Job specs

One file describes a service completely

Specs are HCL — if you have written Nomad job files the shape will be familiar. The minimal service is just an image: three lines deploy, or skip the file entirely with kanea run --image nginx:1.27-alpine. Everything below is optional, and every layer of it is validated before anything moves.

shop.hcl
# A service, its network policy, its TLS, and when to add replicas.
service "web" {
  project = "shop"
  count   = 3

  task "app" {
    image = "registry.example.com/shop/web:1.4.0"

    env = {
      NODE_ENV      = "production"
      DATABASE_URL  = "secret:shop/database-url"   # never inlined
      DATABASE_HOST = "${service.postgres.host}"    # → postgres.shop.kanea
    }

    resources {
      cpu    = 500   # MHz
      memory = 512   # MiB
    }
  }

  network {
    port "http" { container = 3000 }
    policy { allow_from = ["analytics/collector"] }  # else: default-deny
  }

  expose {
    domains = ["shop.example.com"]
    tls { mode = "acme" }
    rate_limit {
      requests = 100
      window   = "1m"
      per      = "ip"
      burst    = 20
    }
  }

  health_check "http" {
    type     = "http"
    path     = "/healthz"
    port     = "http"
    interval = "10s"
    failures = 3
  }

  scaling {
    min = 2
    max = 10
    metric "cpu" { target = 70 }   # percent of resources.cpu
    metric "rps" { target = 500 }  # from eBPF, not from a sidecar
    cooldown = "2m"
  }

  update {
    strategy     = "rolling"
    max_parallel = 1
    min_healthy  = "30s"
  }
}

kanea plan gives you the diff before kanea run applies it. Secrets are referenced as secret:<path>, scoped to their own project at validation time, and injected as tmpfs files — a spec that reaches for another project's secret fails to parse, not at runtime.

What ships

Everything is in the one binary

No agents to install alongside it, no operator to reconcile the operator, no separate metrics stack to stand up first.

Live dashboard

React and shadcn/ui, embedded in the binary and served by the daemon over one multiplexed websocket: services, allocs, events, logs, backups — and a Settings page where the backup destination and notification channels change at runtime. kanea ui opens it.

MCP server

Twenty tools in three tiers, over stdio and streamable HTTP, so an agent can operate the platform. Tools reach it only over its own HTTP API — never a side channel — and no tool at any tier returns a secret.

GitOps & pipelines

In-process git sync, HMAC-signed webhooks, and rootless BuildKit builds. Builds are serialised and refused when full — never silently queued behind a wall.

eBPF autoscaling

CPU, memory, requests-per-second and p95 latency, scraped from containerd, the datapath's own counters and the edge. The autoscaler writes one number and the reconciler converges — it is not a second scheduler.

Notifications

Telegram, Slack, Discord, ntfy, SMTP and generic webhooks, filtered by glob and coalesced. Egress is checked at dial time against every resolved address; redirects are refused.

Backups & DR

AEAD-encrypted archives replicated to S3 by change data capture, with staged and offline restore. A truncated archive cannot restore cleanly to half a platform, and a new destination is probed with a test write before it replaces a working one.

Auth & audit

Deny-by-default on every API, websocket and MCP route. Accounts and tokens live in the store, OIDC with PKCE and LDAP (TLS-mandatory, deny-by-default group mapping) sign in beside them, and every privileged action is audited.

Signed releases

Keyless Sigstore signatures bound to the release workflow itself — no long-lived signing key to guard, rotate, and eventually leak. The proof is in a public transparency log.

Install

Two steps, and none of them are hidden

The installer fetches the binary, verifies it, and stops. It generates no keys and starts nothing — those are decisions with consequences, and a script that made them for you would be making them at the moment you understand the node least. kanea init then installs the runtime itself: containerd, runc and rootless buildkitd, at versions pinned by SHA-256 inside the binary — the network layer needs no component, its eBPF programs travel inside kanea. Under its own prefix, on its own socket — a node that ran Docker yesterday runs it tomorrow.

  1. Install the binary

    Checksum verification is mandatory. If cosign is on PATH, the Sigstore signature is verified too.

    curl -fsSL https://m18h.github.io/kanea/install.sh | sudo bash

  2. Run the first-install ceremony

    Checks the node, installs the runtime, runs the master-key ceremony, writes the systemd units — then starts the control plane, asks for your admin username and password, and prints where everything is: the dashboard URL, the internal DNS address, the subnet layout. Have somewhere to record the key before you start: it is shown once, and without it every backup is unreadable.

    sudo kanea init

    Every component is pinned by version and SHA-256 in the binary — that table is also the version matrix kanea doctor enforces, so there is no second copy to drift. kanea install --list shows it; --dry-run downloads and verifies everything without writing a byte. Already running a containerd you want to keep? --containerd external adopts it instead.

  3. Deploy something

    kanea run --image nginx:1.27-alpine --name web --project demo

Or install it by hand

Same artefacts, same verification, nothing piped anywhere. Replace VERSION with a release tag.

manual install
VERSION=v0.11.0; ARCH=amd64
BASE=https://github.com/m18h/kanea/releases/download/$VERSION

curl -fLO $BASE/kanea_${VERSION#v}_linux_$ARCH.tar.gz
curl -fLO $BASE/checksums.txt
curl -fLO $BASE/checksums.txt.sig
curl -fLO $BASE/checksums.txt.pem

# The signature covers checksums.txt; checksums.txt covers every archive.
cosign verify-blob \
  --certificate checksums.txt.pem \
  --signature   checksums.txt.sig \
  --certificate-identity-regexp "https://github.com/m18h/kanea/" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  checksums.txt

sha256sum --ignore-missing -c checksums.txt
tar xzf kanea_${VERSION#v}_linux_$ARCH.tar.gz
sudo install -m 0755 kanea /usr/local/bin/kanea

That is the whole list. containerd, runc and rootless buildkitd are installed by kanea init at pinned versions — Kanea supplies them, not you.

Air-gapped nodes

A node with no egress is a supported installation, not a workaround. Build a bundle where there is a network, carry it across, install from it. The same hashes govern both paths, so it is the same code — not a second installer that rots between releases.

air-gapped install
# on a machine with a network
kanea bundle create --arch amd64 -o kanea-bundle.tar.gz

# on the air-gapped node
sudo kanea init --bundle kanea-bundle.tar.gz

The bundle carries no hashes of its own. Its contents are checked against the ones compiled into the installing node's binary — a bundle that supplied its own would be a bundle that authenticates itself. Releases publish one per architecture, covered by the same signed checksums.txt.

kanea doctor checks all of this on a live node — dependencies, versions, bpffs, disk and clock — and kanea init refuses to proceed if the node cannot support what it is about to be given.
