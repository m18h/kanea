Reference

CLI reference

Every kanea command, with its usage line, flags and defaults. Kanea is one binary: the same file is the CLI, kanead and the edge.

Services are addressed as project/service, or as a bare service name with --project. Two commands have a second spelling: kanea apply is kanea run, and kanea rm is kanea remove. Run kanea with no arguments to list every command.

Where a command talks

A client command talks to kanead over the local unix socket unless you name a remote endpoint. Every command marked "client" on this page takes these four flags; they are not repeated in the tables below.

FlagEnvironmentDefaultMeaning
--socket-/run/kanea/kanead.sockThe kanead control socket.
--urlKANEA_URL-Base URL of a remote control API, for example https://node:8600.
--tokenKANEA_TOKEN-Bearer token for the remote endpoint.
--ca-certKANEA_CA_CERT-The remote endpoint's CA: a PEM file, or the PEM text itself.

A flag you pass beats its environment variable, and an empty variable counts as unset. Passing --socket makes the call local and ignores KANEA_URL. Combining --socket with --url, --token or --ca-cert is refused.

The socket is root-owned, so local client commands run under sudo. To drop the sudo, join the kanea group that kanea init creates and log in again: sudo usermod -aG kanea <user>. Membership is root-equivalent, like docker's group.

Remote nodes and CI covers the token, the CA and pipeline examples.

Setup

kanea init

Sets up a node: preflight checks, host components, the master-key ceremony, the node config, the systemd units and the first admin account. Run it once, as root. 

sudo kanea init [flags]
FlagDefaultMeaning
--data-dir/var/lib/kaneaState directory.
--log-dir/var/log/kanea/allocsWorkload log directory.
--unit-dir/etc/systemd/systemWhere the systemd units are written.
--prefix/usr/local/lib/kaneaWhere component binaries are installed.
--node-cidr10.244.0.0/24This node's container subnet. Its .1 is the internal DNS address.
--cluster-cidr10.244.0.0/16The range treated as internal. It must contain --node-cidr.
--node-cidr6-This node's IPv6 container subnet. Opt-in; needs the other two *6 flags.
--cluster-cidr6-The routed IPv6 range. It must contain --node-cidr6.
--service-cidr6-IPv6 pool for service addresses.
--containerd/run/kanea/containerd.sockcontainerd socket. external adopts the containerd already on the host.
--buildkitunix:///var/lib/kanea/buildkit/run/buildkitd.sockRootless buildkitd address. off skips the build daemon.
--listen127.0.0.1:8600API/dashboard network address written to /etc/kanea/kanea.hcl. none keeps it socket-only.
--listen-cert-TLS certificate for --listen.
--listen-key-TLS private key for --listen.
--reserve256MMemory reserved for the control plane.
--admin-userpromptThe first admin's username. With a piped password, init runs unattended.
--timeout2mHow long to wait for kanead to come up.
--bundle-Install the host components from an offline bundle.
--no-installoffSkip the host components and assume they are present.
--no-startoffWrite the files, but do not start kanead or create the first account.
--skip-checksoffRun the ceremony without the preflight checks.
--skip-unitsoffDo not write systemd units.

Init writes its directory, network and listener choices to /etc/kanea/kanea.hcl. A value already in the file is kept unless you pass the matching flag. When the file has a bind stanza and you do not pass --listen, init skips the listen question and leaves the stanza alone.

A --listen address beyond loopback is served over TLS. Without a --listen-cert/--listen-key pair, init creates a self-signed pair at /etc/kanea/api.crt and api.key. An address with no host, such as 0.0.0.0:8600 or :8600, is refused.

Re-running init is safe: an existing master key and an existing account are left alone. Install a node has the annotated walk-through.

The key is shown once

The ceremony prints the master key and makes you type it back. Without that key every backup this node makes is unreadable, so have somewhere to record it before you start.

kanea bundle

Builds an offline bundle of the host components on a machine with a network, for a node without one. Its only subcommand is create. 

kanea bundle create [flags]
FlagDefaultMeaning
--archhost architectureTarget architecture: amd64 or arm64.
-okanea_<version>_linux_<arch>_bundle.tar.gzOutput path.
--diroffWrite a directory instead of a tarball.
--no-imagesoffOmit buildkit. For a node that runs no builds, with builds.buildkit_addr = "off".

kanea doctor

Verifies the node and exits non-zero when a check fails. It reads the settings it checks against from the node config. Safe to run at any time. 

kanea doctor [--prefix=/usr/local/lib/kanea] [--offline]
FlagDefaultMeaning
--prefix/usr/local/lib/kaneaComponent install prefix.
--offlineoffSkip the upstream reachability probe. Use it on air-gapped nodes.

It checks component versions against the pins, the containerd and build sockets, bpffs, cgroups v2 and slice placement, the kernel, the memory floor, subnet overlap, the state database's permissions, disk headroom and clock synchronisation. It also names a host firewall that drops alloc traffic.

A /etc/kanea/kanea.hcl that does not load is a failed check, and the other checks still run. A check that needs root is reported SKIP, and the run ends by saying how many were skipped. Warnings do not change the exit code.

kanea firewall

Prints the host-firewall rules this node's workloads need. It prints and never applies them. 

kanea firewall [--manager=ufw|firewalld|nft|iptables] [--all] [--prefix=/usr/local/lib/kanea]
FlagDefaultMeaning
--managerdetectedPrint rules for one manager: ufw, firewalld, nft or iptables.
--alloffPrint every manager's rules.
--prefix/usr/local/lib/kaneaComponent install prefix.

The rules come from this node's own network stanza. There are two: forward, for alloc traffic leaving the node, and input, for allocs reaching the internal resolver.

Kanea writes only its own kanea nftables table. A rule it placed in a manager's ruleset would be flushed on that manager's next reload, so you add the rules yourself. A published port needs its own inbound allow, which this command does not print.

kanea config

Converts an older unit's command-line flags into /etc/kanea/kanea.hcl. Its only subcommand is migrate. 

sudo kanea config migrate [--unit-dir=/etc/systemd/system] [--dry-run]
FlagDefaultMeaning
--unit-dir/etc/systemd/systemWhere kanead.service and kanea-edge.service live.
--dry-runoffPrint the resulting file and the two new ExecStart lines, write nothing.

sudo kanea upgrade runs this conversion for you. Migrating from flags explains what it reads and what it rewrites.

kanea ca

Shows the node's own CA certificate, which devices install to trust self-signed services and the dashboard. Client command. 

kanea ca show [--out=FILE] [--quiet]
kanea ca info
SubcommandFlagDefaultMeaning
showPrints the certificate in PEM on stdout and installation hints on stderr.
--outstdoutWrite the PEM to this file.
--quietoffOmit the installation hints.
infoPrints the certificate's subject, fingerprint and validity.
 
kanea ca show > kanea-ca.crt

There is no kanea ca rotate and no command that returns the CA key. Rotating means re-trusting every device.

kanea upgrade

Fetches and verifies a release, installs it over the running binary, takes a backup, then restarts kanea-edge and kanead and waits for health. It acts on this machine only and refuses a remote endpoint. 

sudo kanea upgrade [flags]
FlagDefaultMeaning
--checkoffReport the running, installed and latest versions and stop.
--versionlatestUpgrade to this release, written vX.Y.Z.
--allow-downgradeoffPermit a target older than the running daemon. The Store's schema may not support it.
--no-fetchoffDownload nothing and restart onto the binary already installed.
--require-signatureoffRefuse the release unless its cosign signature verifies. Also on when upgrade.require_signature = true.
--skip-backupoffDo not take the pre-upgrade backup.
--dry-runoffPrint what would run and stop.
--timeout2mHow long to wait for each service.

The release's sha256 is always checked against its checksums.txt. The cosign signature over that file is checked when cosign is installed. Without --require-signature, a missing cosign binary or an unsigned release is a printed note.

The release repository comes from upgrade.repo in the upgrade stanza. When the installed binary is already the target version, nothing is downloaded. When no backup destination is configured, the upgrade says so and continues.

Upgrade and uninstall has the procedure, including nodes whose binary a package manager owns.

Deploying

kanea plan

Shows what applying a spec would change, and changes nothing. Client command. 

kanea plan app.hcl [more.hcl …] [selector …] [--remove-orphans]
kanea plan --image=nginx:1.27-alpine --name=web --project=demo [--count=1]
FlagDefaultMeaning
--remove-orphansoffAlso show what kanea run --remove-orphans would delete.
--image-Plan a single image without a spec file.
--name-Service name, with --image.
--project-Project name, with --image.
--count1Alloc count, with --image.
 
$ kanea plan app.hcl
~ update shop/web
    image             web:v1 -> web:v2  (rolls allocs)
    env               + DB_URL, ~ LOG_LEVEL  (rolls allocs)
    volumes           + cache  s3:backups /var/cache rw 10 GiB budget  (rolls allocs)
                      ~ data  local /data rw -> local /srv/data rw
    expose            + api.example.com  (tls acme, port 8080)
    publish           - 8443/tcp  port http
    scaling           min 1, max 5, rps 100 -> min 1, max 10, rps 100

+ create shop/worker (count 2, image worker:v3)
    volumes           + queue  local /queue
    files             + /etc/app.conf  (412 B, content 3f2a1b9c, mode 0644)
    check             http /healthz on port 8080 every 10s, timeout 2s, 3 failure(s)

Plan: 2 change(s) - 1 create, 1 update; 1 replace running allocs.
Run `kanea run` to apply.

The output has one block per service and one row per resource added, changed or removed. Rows marked (rolls allocs) replace running containers. The other rows are applied to the service as it runs, or republished to the edge.

Several files are parsed as one set, so their order does not matter. The spec is parsed and validated with file-and-line diagnostics before anything dials kanead. Validation errors fail the plan. Weak defaults only warn: an effective uid of 0, a writable root filesystem, or a moving image tag without auto-update.

A plan never prints an environment value or a config file's content, because either may carry a secret. You get the keys, the paths and a short digest of the content.

Selectors

A selector scopes plan and run to part of the file: shop/web is one service and shop is a whole project. Several selectors union. An argument that exists on disk is a spec file, and any other argument is a selector.

The whole file is still parsed and validated, and every selector must match at least one service in it.

kanea run

Applies a spec. kanea apply is the same command. Client command. 

kanea run app.hcl [more.hcl …] [selector …] [--wait=60s] [--remove-orphans] [--yes]
kanea run --image=nginx:1.27-alpine --name=web --project=demo [--count=1]
FlagDefaultMeaning
--wait60sHow long to wait for allocs to run. 0 returns immediately.
--remove-orphansoffDelete services in this spec's projects that the spec does not declare.
--yes, -yoffApply without asking. Implied when stdin is not a terminal.
--image-Run a single image without a spec file.
--name-Service name, with --image.
--project-Project name, with --image.
--count1Alloc count, with --image.

On a terminal, run prints the plan and asks Apply? [Y/n]. Enter applies; any answer other than y or yes aborts and sends nothing. With a piped or redirected stdin it applies without asking, so CI jobs do not need --yes.

Running it twice with an unchanged spec does nothing. An apply is additive: a service the spec does not declare keeps running, and a scoped run cannot delete anything.

--remove-orphans deletes what the spec does not declare, in each project the spec has a project block for. The deletes and the applies go in one atomic batch. It is refused with a selector and with --image, because neither sends a whole project. Read what a prune destroys first.

--image creates a bare service from project, name, count and image. It refuses to overwrite a service that declares more than that, and names what would be lost. To change the image of an existing service, use kanea deploy.

kanea deploy

Points an existing service at a new image and leaves the rest of its spec alone. This is the command for a CI pipeline's last step. Client command. 

kanea deploy [--project=P] <[project/]service> <image> [--wait=60s] [--no-wait]
FlagDefaultMeaning
--project-Project name, for a bare service name.
--wait60sHow long to wait for the new image to be running.
--no-waitoffReturn once the change is accepted.
 
kanea deploy shop/web registry.example.com/shop/web:v2

An init step that declared the previous image moves to the new one, and the output names the steps that followed. A step on any other image is untouched. Deploying a new image has the pipeline examples.

kanea stop

Scales a service to zero. Client command.

kanea stop [--project=P] [--rm] [--yes] <[project/]service>
FlagDefaultMeaning
--project-Project name, for a bare service name.
--rmoffAlso delete the service declaration. Asks first on a terminal, as kanea remove does.
--yes, -yoffRemove without asking. Implied when stdin is not a terminal.

kanea remove

Deletes one service declaration. kanea rm is the same command. Client command. 

kanea remove [--project=P] [--yes] <[project/]service>
FlagDefaultMeaning
--project-Project name, for a bare service name.
--yes, -yoffRemove without asking. Implied when stdin is not a terminal.

It asks [y/N] on a terminal. The containers, alloc records, VIP, routes and mounts go. Volume data is kept, so re-applying the spec brings the service back with its data.

kanea start

Scales a stopped service back up. Client command.

kanea start [--project=P] <[project/]service> [count]

Its one flag is --project. A stopped service does not remember its earlier count, so start brings up one replica unless you give a count. An autoscaled service starts at its declared minimum. A service that is already running is left as it is.

kanea restart

Rolls a service's allocs through its update policy. Client command. 

kanea restart [--project=P] <[project/]service>

Its one flag is --project. A restart also clears an exhausted crash-restart budget, because the budget belongs to the generation that spent it.

Inspecting

kanea ps

Lists allocs: id, service, state, health, restarts, age and address. Client command. 

kanea ps [--project=P] [--service=S] [-a]
FlagDefaultMeaning
--project-Filter by project.
--service-Filter by service.
-a, --alloffAlso show what is declared but not running.

A removed alloc leaves no record, so a stopped service does not appear by default. -a adds services scaled to zero as stopped, and slots not yet created as pending.

kanea describe

Shows one service in full: the declared spec beside what is true on the node. Client command. 

kanea describe [--project=P] <[project/]service>

Its one flag is --project. The output covers the image and its pinned digest, routes, volumes and grants, the alloc table with health verdicts, a stats snapshot and recent events. A missing metric prints as -, never as zero.

The alloc table's REASON column says why each alloc last stopped, or why it never ran:

ReasonMeaning
OOMKilledKilled for memory. Read from the alloc's cgroup, not guessed from exit code 137.
SignalledStopped by a signal, which includes a forced stop.
Error, CompletedExited non-zero, or exited zero.
ImageFailed, VolumeFailed, GrantFailed, NetworkFailed, CreateFailed, StartFailedNever ran, and the step that failed.

The reason is about the last stop. A running row that carries OOMKilled is up now and was killed for memory the time before.

kanea status

kanea logs

kanea logs [-f] [--tail=N] [-c NAME] [--previous] [--project=P | --alloc=ID] [[project/]service]
FlagDefaultMeaning

Scaling and builds

kanea scale

Sets a service's desired count and returns. Client command.

kanea scale [--project=P] <[project/]service> <count>

Its one flag is --project. kanead converges on the new count afterwards. A count outside an autoscaled service's declared bounds is refused.

kanea build

Triggers a service's build pipeline. Client command.

kanea build [--project=P] [--deploy=true] [--follow=true] <[project/]service>
FlagDefaultMeaning
--project-Project name, for a bare service name.
--deploytrueDeploy the built digest when the build succeeds.
--followtrueStream the build log until it finishes.

Builds run one at a time. A second build is queued, and refused when the queue is full.

kanea images

Lists the node's containerd images per project: size, age and whether anything still references each one. Client command. 

kanea images [--clean] [--json]
FlagDefaultMeaning
--cleanoffRemove unused images now, in one GC sweep. Admin-only and audited.
--jsonoffMachine-readable output.

--clean reports what it removed and how much it reclaimed. The rules it deletes under are in the image GC reference. On a node whose pull_policy is "never" the sweep is refused, because preloaded images cannot be pulled again.

kanea volume

Lists every storage resource with the mounts that use it: driver, location, measured usage, declared budget and mount state. Its only subcommand is list. Client command. 

kanea volume list [--json]
FlagDefaultMeaning
--jsonoffMachine-readable output.

Usage is sampled in the background. A volume reads - until it has been measured, and s3 volumes are never measured. A local volume appears once per alloc, each with its own contents and its own budget.

Volumes are created and deleted by the spec that declares them, so there is no subcommand for either.

Backup and restore

kanea backup

Creates, lists and verifies backup archives through the running kanead. Client command. 

kanea backup create [--reason="on-demand"]
kanea backup list
kanea backup verify <archive-id>
SubcommandFlagDefaultMeaning
createTakes a backup now. now is the same subcommand.
--reasonon-demandRecorded in the archive manifest.

kanea restore

Restores the node's state from a backup. It has two forms. Without --from it is a client command that asks the running kanead to stage a restore. With --from it works offline and needs no kanead. 

kanea restore [--snapshot=ID] [--skip-replay]
kanea restore --from=DIR|s3://bucket/prefix [--snapshot=ID] [--skip-replay] [--target=PATH]
              [--master-key=PATH] [--data-dir=/var/lib/kanea]
              [--s3-endpoint=…] [--s3-region=…] [--s3-access-key=…]
              [--s3-secret-key-file=PATH] [--s3-path-style=true]
FlagDefaultMeaning
--snapshotthe newestArchive id to restore.
--skip-replayoffRestore the snapshot without its change segments. Everything after the snapshot is lost.
--from-Restore offline from a destination: a directory, or s3://bucket/prefix.
--target<data-dir>/state.dbWhere to write the restored state.
--master-key<data-dir>/master.keyMaster key file.
--data-dir/var/lib/kaneaNode data directory.
--s3-endpoint-S3 endpoint URL.
--s3-region-S3 region.
--s3-access-key-S3 access key id.
--s3-secret-key-file-File holding the S3 secret key. The key is never an argument.
--s3-path-styletrueAddress the bucket as /bucket/key.

The flags from --target down apply only with --from. A staged restore changes nothing until you restart kanead, which applies it at startup before it opens the Store. The offline form writes a state file for a node that has lost its disk.

Back up a node points to the full recovery procedure. The API and the dashboard have no restore action.

Daemons

systemd runs these two commands; you do not run them by hand. Both read /etc/kanea/kanea.hcl once at startup. The node config reference lists every attribute.

kanea agent

Runs kanead, the control-plane daemon. kanead.service starts it. 

kanea agent

It takes no flags and no arguments. Any argument is refused with this message: 

kanea agent takes no arguments: node configuration lives in /etc/kanea/kanea.hcl. To convert an older unit's flags: sudo kanea config migrate

To change a setting, edit the file and run sudo systemctl restart kanead. Applying a change has the steps.

kanea edge

Runs the edge, the ingress proxy. It is its own process, started by kanea-edge.service, so north-south traffic survives a kanead restart. 

kanea edge

It takes no flags and no arguments, and refuses any argument the way kanea agent does. Its settings are the edge stanza and the edge_* attributes of bind. Restart kanea-edge after changing them.

Runs a stdio MCP server for an AI agent on the node. It uses the local socket only and refuses a remote endpoint.
