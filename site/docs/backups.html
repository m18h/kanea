Guides

Back up a node

Point the node at a directory or an S3 bucket and it replicates its state there continuously. This page sets that up and shows how to check an archive.

A backup holds the Store: projects, services, secrets, certificates and accounts. It does not hold volume data or images. kanead writes a full snapshot every six hours and ships the changes since the last one every minute.

Keep the master key somewhere else

Archives are encrypted with keys derived from the node's master key, which kanea init shows once. The key is not in the backup. Without it every archive is unreadable.

Set a destination

There are two places to set one: the backup stanza of the node config, or the dashboard. Use the stanza for a node you manage from files. Use the dashboard to change the destination without a restart.

In the node config

  1. Store the S3 secret key

    The node config holds a reference to the key and never the key. Skip this step for a directory destination. 

    kanea secret put shared/backup-s3 < s3-secret-key.txt

  2. Add the backup stanza

    Name one destination: dir or the s3 block. An S3 destination needs an explicit endpoint, because Kanea does not guess one from the region. 

    # /etc/kanea/kanea.hcl
backup {
  s3 {
    url        = "s3://kanea-state/home"
    endpoint   = "https://s3.eu-central-1.amazonaws.com"
    region     = "eu-central-1"
    access_key = "AKIAEXAMPLE"
    secret_key = "secret:shared/backup-s3"
  }
}

    For a directory, such as a mounted disk, the stanza is one line:

    backup {
  dir = "/mnt/backup/kanea"
}

  3. Restart kanead and check replication

    sudo systemctl restart kanead
kanea backup list

    The first line names the destination. kanead takes a snapshot at every start, so an archive with the reason startup appears shortly after.

A destination in the stanza that cannot be built stops kanead from starting, so a typo is found at once. Intervals and retention are in the backup reference.

In the dashboard

  1. Open Settings and choose the Backup tab

    You need an admin account. The page shows the current destination and where it came from.

  2. Enter a directory or an S3 bucket

    The S3 secret key field takes a reference such as secret:shared/backup-s3. A pasted key is refused.

  3. Save

    kanead writes a test object to the new destination before it changes anything. If the test fails, the save is refused and the old replication keeps running.

On a successful save the old destination receives one last segment, and the new one gets a full snapshot straight away. No restart is involved.

Which setting wins

A destination saved in the dashboard wins. The backup stanza is the fallback.

Saved in the dashboardbackup stanzaThe node replicates to
YesAnyThe saved destination. The stanza's intervals and retention are ignored too.
NoNames a destinationThe stanza's destination.
NoNo destinationNowhere. Backups are off.
  • Revert to kanea.hcl in the dashboard deletes the saved destination. The node returns to the stanza, or to no backups if the stanza names none.
  • If the saved destination cannot be read or built at startup, kanead logs an error and uses the stanza.
  • The Backup tab labels the active destination from settings or from kanea.hcl.

The saved destination lives in the Store. A blank node has no Store yet, so backup.restore_if_empty can only use the stanza. If you rely on that setting, keep the stanza pointing at the same place as the dashboard.

Create, list and verify archives

kanea backup create [--reason="before upgrade"]
kanea backup list
kanea backup verify <archive-id>
CommandWhat it does
createTakes a snapshot now and prints the archive id. Retention applies as it does to a scheduled snapshot.
listShows the destination, the last snapshot and segment, any failures, and one row per archive.
verifyReads the archive's snapshot from the destination and compares its size and SHA-256 hash with the manifest.

verify also checks the manifest's own authentication code. On success it prints that the archive is intact. A damaged archive is an error that names the object.

It does not decrypt the snapshot and does not replay change segments. It proves the bytes are intact, not that a restore works. For that, restore to a scratch path as the runbook's drill describes.

All three commands go through the running kanead. The Backups page of the dashboard lists the same archives, checks them, and stages a restore.

Restore

SituationWhat to do
The node lost its diskPut the master key back, run kanea restore --from <directory or s3://bucket/prefix> with kanead stopped, then start kanead.
The node is up but wrongRun kanea restore --snapshot <archive-id>. It verifies the archive and stages the restore, and kanead applies it at its next start.
A blank node should restore itselfSet backup.restore_if_empty = true in the stanza. A node with no state then restores the newest archive at its first start.

Nothing restores in place. A staged restore moves the current state aside as state.db.before-restore-<timestamp> and never deletes it.

The two restores that run at kanead's start read the destination from the backup stanza, before the Store is open. They cannot resolve a secret: reference, so they work with backup.dir. For an S3 destination, use kanea restore --from s3://….

The full procedure, with the flags and a drill, is in the disaster recovery runbook. Read it before you need it.
