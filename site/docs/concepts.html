Concepts

Kanea asks you to learn about seven terms. This page defines them, maps them to the systems you may already know, and explains what makes the node start, replace or leave alone a container. The glossary at the end is the short version.

The terms

Kanea borrows from Nomad and Kubernetes and keeps the smallest set of concepts that covers the work. If you know either system, the middle columns show what maps to what. If you come from a managed cloud service, use the ECS and Container Apps table instead.

The one that surprises people is project. It is a boundary that four subsystems enforce independently, where a label would only describe. A service in project shop, on a node that also runs project analytics:

  • cannot reach a service in analytics unless a spec says so;
  • cannot read analytics' secrets, even by naming them;
  • runs its containers in a separate containerd namespace;
  • has its DNS names under a separate suffix.

"Task" means the opposite thing in ECS

In ECS a task is a running instance: the unit a service keeps desiredCount of, and the equivalent of a Kubernetes pod. In Kanea that is an alloc. A Kanea task is the container inside a service, which ECS calls a container definition.

So "three tasks" means three replicas on ECS. In Kanea a service has exactly one task and, at count = 3, three allocs.

Where the mapping breaks down

  • Project has no ECS equivalent. ECS groups by cluster and otherwise relies on IAM and tags. Nothing there carries network policy, secret scope and DNS at once. On Container Apps the environment is both the hosting boundary and the network boundary, so it appears twice in the table. Kanea splits those into the node and the project.
  • One node, not a region. Both services schedule across availability zones and survive a machine dying. Kanea is a single machine, and if it stops, everything on it stops. What it offers in place of failover is state replication and restore: an encrypted snapshot and change log in S3, restored onto a new machine.
  • There is no control plane to rent. kanead is a process on your machine inside a 256 MiB memory reservation. Patching, capacity and the node's uptime are yours.
  • Load balancing is in the datapath. A service gets a VIP the moment it exists, and eBPF rewrites traffic between services at connect() without a proxy. On ECS the equivalent is a load balancer, a target group and listener rules that you declare and pay for. Traffic from outside goes through the edge, a process on the same machine.
  • The spec is one file for the whole project. An ECS deployment is typically a task definition, a service definition, target groups and listener rules, assembled by Terraform or CDK. A Kanea project is one HCL file covering containers, routing, TLS, volumes, scaling and builds, and kanea plan validates it offline.

Naming

Project and service names must be DNS-1123 labels: lowercase letters, digits and -, starting and ending with a letter or digit, at most 63 characters. Kanea checks this when it parses the spec.

The rule lets names compose into DNS without an escaping step. A service web in project shop is web.shop.kanea internally and web.shop.<base_domain> publicly. Domains and HTTPS covers both forms.

Where the prose goes

Every project and service takes a description: free text, up to 512 characters, shown in the dashboard. Put the human-readable detail there and keep the name a label.

Lifecycle

Nothing is applied directly to the runtime. A spec becomes desired state in the Store, and a reconciler keeps converging the node toward it. 

Spec (HCL) ──────parse/validate──▶ Desired state (Store)
                                        │
                                   Reconciler loop
                                        │
                        ┌───────────────┼────────────────┐
                        ▼               ▼                ▼
                    containerd      eBPF datapath    Edge proxy
                   (tasks/images) (policy/LB)       (routes/TLS)
                        │               │                │
                        └───────────────┴────────────────┘
                                        ▼
                            Actual state / events / metrics

What follows from that:

  • Drift is repaired. Delete a container by hand and it comes back. The reconciler compares desired state with the node; it keeps no memory of what it did.
  • Restart policies are always (the default), on-failure with backoff, and never.
  • Updates are rolling by default, gated on health and bounded by max_parallel.
  • Dependencies start first. A depends_on edge means the dependent waits until its dependency is healthy. Any ${service.…} reference creates the same edge implicitly. If the dependency degrades later, dependents keep running and Kanea emits events.
  • Storms are capped. Each service has a restart rate limit. A node-wide circuit breaker pauses rollouts and scale actions when failure rates spike, and a trip emits an event and a notification.

What counts as a deploy

A deploy is a spec-hash mismatch. The reconciler hashes the parts of a service that are fixed into a container when it is created. If an alloc's recorded hash differs from the current one, the update policy replaces that alloc. If it matches, nothing happens, however many times you run kanea run.

kanea restart uses the same path. It bumps a generation counter that is part of the hash, and the ordinary rolling update does the rest.

Two things about rolling updates

max_parallel bounds allocs that are down, not replacements in flight. Anything already unavailable spends the budget first, so a deploy that starts going wrong stops before it walks through every replica.

min_healthy applies only to allocs the current deploy has already replaced, and healthy means a probe said so. A service with no health_check block never reports healthy, and the update proceeds without waiting for it.

Glossary

The rest of the documentation uses these words in exactly these senses.

TermMeaning
nodeThe one Linux machine Kanea runs on. It hosts kanead, the edge and every alloc.
kaneadThe control-plane daemon: API, dashboard, reconciler, autoscaler, GitOps, notifications and backups. It is the kanead systemd unit, started by kanea agent.
the edgeThe ingress proxy, kanea-edge. It terminates TLS on ports 80 and 443 and routes each request by host to a service. It is a separate systemd unit under an unprivileged user, started by kanea edge.
projectA named group of services and the isolation boundary for network policy, secrets, containers and DNS.
serviceA long-running workload inside a project: one task (the container) kept at count replicas.
allocOne running instance of a service, with its own network namespace, address and resource limits.
specThe HCL file that describes one project: its services, storage, routing, scaling and builds. kanea plan validates it and kanea run applies it. See the spec reference.
node configThe file /etc/kanea/kanea.hcl. It holds every setting of the node itself, and both daemons read it once at startup. See the node config reference.
grantA host device or unix socket the operator names in the node config, with the projects allowed to use it. A spec asks for a grant by name and never names a host path. See device and socket grants.
StoreThe embedded database inside kanead that holds desired state, allocs, events, certificates, secrets and the audit log. See the Store.
VIPThe virtual IP each service gets from the service CIDR. A connection to it is rewritten to one of the service's allocs when it is opened.
