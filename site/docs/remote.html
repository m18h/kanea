Remote nodes and CI

Run the kanea CLI from a laptop or a CI runner against a node's HTTPS listener, and deploy a new image from a pipeline.

A remote CLI presents the same token the REST API and the MCP endpoint accept. The role decides what it may do: a viewer token reads everything and changes nothing.

Set up a remote CLI

The node needs a network listener first. If kanea ui on the node prints a loopback address or an error, follow Change the listen address.

  1. Install the CLI on your machine

    Use Homebrew or a release archive. The CLI is one static binary and needs no node beside it. kanea version prints the version.

  2. Create a token, on the node

    sudo kanea token create --role admin --expires-in 720h ci > token.txt

    The secret goes to stdout once and token.txt now holds it. Deploying needs --role admin. For a job that only inspects, create a viewer token. Sign-in and access covers listing and revoking.

  3. Export the node's CA, on the node

    sudo kanea ca show > kanea-ca.crt

    Copy kanea-ca.crt to your machine. Skip this step when the node's listener uses api_tls = "acme": public roots already trust that certificate.

  4. Point the CLI at the node

    export KANEA_URL=https://kanea.apps.example.com:8600
export KANEA_TOKEN=$(cat token.txt)
export KANEA_CA_CERT=/path/to/kanea-ca.crt

kanea ps

    kanea ps lists the node's allocs. The CLI is now remote.

Flags and environment

VariableFlagValue
KANEA_URL--urlThe node's API address: scheme, host and port, with no path.
KANEA_TOKEN--tokenThe bearer token. An empty value counts as unset.
KANEA_CA_CERT--ca-certA PEM file path, or the PEM text itself.

A flag you pass beats the environment. An explicit --socket keeps one command local even with KANEA_URL exported.

KANEA_CA_CERT accepts the PEM itself because CI systems hand secrets to a job as values: 

KANEA_CA_CERT="$(cat kanea-ca.crt)"     # or a CI variable holding the PEM

There is no flag to skip certificate verification. The CLI also refuses an http:// endpoint beyond loopback, because the token would cross the network in clear text.

Deploy a new image

kanea deploy [--project P] <[project/]service> <image> [--wait 60s] [--no-wait]

kanea deploy points an existing service at a new image and leaves the rest of its spec as declared: 

kanea deploy shop/web ghcr.io/acme/web@sha256:9f2a…

It waits for the new image to be running and exits non-zero if it is not, so a failed deploy fails the pipeline. --no-wait returns once the change is accepted.

Prefer a digest to a tag. A tag can move between two allocs being replaced, and then they run different code.

SituationWhat deploy does
An init step declares exactly the task's previous imageMoves that step to the new image too, so a migration runs the same build as the app. The command names the steps that followed.
An init step uses any other imageLeaves it alone.
The service already declares this image and its allocs are healthyReports it and does nothing. Re-running a pipeline on an unchanged commit succeeds.
The service already declares this image and its allocs have failedRestarts the service.
Old allocs had failed before the deployShows them as replacing and does not count them. Only a failure on the new image fails the command.
Use deploy, not kanea run --image, on an existing service

kanea run --image builds a bare service from a name, a count and an image. Over an existing service it would delete ports, expose, env, volumes, health checks and scaling, so it refuses and names what would be lost.

Deploy from a pipeline

Store the token and the CA as CI secrets, set KANEA_URL, and run kanea deploy after the image is pushed.

The container image

The CLI ships as ghcr.io/m18h/kanea, tagged vX.Y.Z and latest. Pin the version in a pipeline. Its entrypoint is kanea, so a runner that passes a shell script as the command needs the entrypoint cleared, as the GitLab job below does.

The container image lists what is in it and how to verify its signature.

GitLab

.gitlab-ci.yml
deploy:
  stage: deploy
  image:
    name: ghcr.io/m18h/kanea:vX.Y.Z           # pin the version
    entrypoint: [""]                          # GitLab runs the job script as the container command
  variables:
    KANEA_URL: https://kanea.apps.example.com:8600
  script:
    - kanea deploy shop/web "$CI_REGISTRY_IMAGE@$IMAGE_DIGEST"
  # KANEA_TOKEN: masked project variable
  # KANEA_CA_CERT: a file variable, or the PEM as a masked variable

GitHub Actions

.github/workflows/deploy.yml
- name: Deploy
  # or run the image directly: docker run --rm -e KANEA_URL -e KANEA_TOKEN \
  #   ghcr.io/m18h/kanea:vX.Y.Z deploy shop/web "$IMAGE"
  env:
    KANEA_URL: https://kanea.apps.example.com:8600
    KANEA_TOKEN: ${{ secrets.KANEA_TOKEN }}
    KANEA_CA_CERT: ${{ secrets.KANEA_CA_PEM }}
  run: kanea deploy shop/web "ghcr.io/acme/web@${{ steps.build.outputs.digest }}"

Commands that stay on the node

Two commands refuse a remote endpoint:

  • kanea upgrade restarts this host's units and installs a binary over this host's. Run it on the node or over ssh.
  • kanea mcp serves MCP over stdio with the local socket as its credential. A remote agent uses the node's /mcp endpoint with a token.

kanea init, install, bundle, doctor, firewall and config migrate take no endpoint: they act on the host they run on. Everything else works remotely, including kanea exec and kanea logs -f.

Let the node pull instead

A token in CI is one way. The other is to have the node watch a git repository, with CI committing the new digest instead of calling the node.

  1. The pipeline builds and pushes the image, then commits the new digest into the spec repository the project's git block names.
  2. The push fires the webhook, POST /v1/webhooks/git/<project>. The node checks GitLab's X-Gitlab-Token or GitHub's X-Hub-Signature-256 against the project's webhook_secret_ref.
  3. The node re-reads the repository with its own credential and applies what it finds. Nothing is deployed from the request, so a forged delivery cannot choose an image.

This needs no token in CI and leaves a git history of every deploy. It costs a spec repository and a commit per release. kanea project sync <project> forces the read without waiting for the poll. The git block is part of the project in the spec reference.
