Domains and HTTPS

Give a service a public name and a certificate. Names between services on the node work without any setup, so most of this page is about the public side.

Kanea has two separate name spaces. One is internal and automatic. The other is public, and it is the only one where you create DNS records.

InternalPublic
Looks likeweb.shop.kaneaweb.shop.apps.example.com
Resolved byKanea's own resolverYour DNS provider
Answers withThe service's VIPThe node's public address
ReachesThe allocs directlyThe edge on :443, then the allocs

Internal names between services

Use the short name. Every alloc gets a generated /etc/resolv.conf that points at Kanea's resolver, with a search path that completes short names: 

nameserver 10.244.0.1
search shop.kanea kanea
options ndots:1 timeout:2 attempts:2

From a service inside project shop:

You writeIt resolvesWhen to use it
dbdb.shop.kaneaA service in the same project.
cache.datacache.data.kaneaA service in another project.
db.shop.kaneaitselfWhen you would rather be explicit.

The answer is the service's VIP. The datapath balances each connection across the service's healthy allocs at connect(), with no proxy in the path.

The resolver listens on the first address of the node CIDR, 10.244.0.1 by default. dns.listen moves it or turns it off.

Resolving is not reaching

A cross-project name resolves for anyone, but the datapath denies traffic between projects by default. The connection is dropped unless the service being called lists the caller in allow_from.

The symptom is a name that resolves and a connection that times out. Check allow_from on the called service before you look at DNS.

Set the base domain

An exposed service's public name is <service>.<project>.<base_domain>. Without a base domain a service has no generated name, so it is reachable by name only through the domains its spec lists.

  1. Add base_domain to the node config

    Edit /etc/kanea/kanea.hcl, the node config. The attribute sits at the top level, outside any stanza. 

    # /etc/kanea/kanea.hcl
base_domain = "apps.example.com"

  2. Restart kanead

    kanead reads the file once, at startup. Running workloads keep running through the restart. 

    sudo systemctl restart kanead
kanea describe shop/web

    The routes of shop/web now include web.shop.apps.example.com.

A spec can name its own domains with expose { domains = […] }. Those work with or without a base domain.

Create the DNS records

One wildcard record covers every generated name, present and future:

RecordTypePoints atCovers
*.apps.example.comAThe node's public IPv4Every generated service name
*.apps.example.comAAAAThe node's public IPv6The same, for v6 clients
kanea.example.comAThe node's addressThe dashboard, if you gave it a name
shop.example.comAThe node's public IPv4One custom domains entry

The AAAA record concerns the node's own public address. The edge binds :443 on whatever addresses the host has, so a node with public IPv6 serves v6 clients whether or not allocs have v6 addresses.

The dashboard is not a service and the wildcard does not cover it. Give it a name with bind.api_domain and point a record at the node. Reaching the dashboard covers its port and certificate.

The records are static once created. The edge routes on the Host header, so scaling or redeploying a service changes nothing in DNS.

Choose where certificates come from

Set tls.default_mode in the node config. It decides the certificate source for every exposed service whose spec does not name one.

ModeCertificate comes fromNeeds
acmeAn ACME CA, Let's Encrypt unless you say otherwise. The default.acme.email, and a way to pass the challenge
self-signedA CA this node generates on first useThe CA installed on each device, once
providedA certificate you put on the nodeA certificate block that allows the project
plaintextNowhere: the service is served over plain HTTPNothing

A spec overrides the node for one service with expose { tls { mode = "…" } }. A mode names a source and never a file path. The attribute tables are in the node config reference, under tls and acme.

Get certificates from Let's Encrypt

  1. Create the DNS record first

    The name must already resolve to the node, and port 80 must be reachable from the internet. The CA checks both during issuance.

  2. Add the acme stanza

    An email address is the only required attribute. Without one kanead requests no certificate from a CA, and services in acme mode are served over plain HTTP. 

    # /etc/kanea/kanea.hcl
base_domain = "apps.example.com"

acme {
  email = "ops@example.com"
}

  3. Restart kanead and check a service

    sudo systemctl restart kanead
curl -I https://web.shop.apps.example.com

    kanead emits a cert.issued event when the certificate arrives. After that the response comes over HTTPS with a publicly trusted certificate.

While you are still getting DNS right, add directory = "staging" to the stanza. The staging CA has much looser rate limits, and its certificates are not trusted by browsers.

HTTP-01 or DNS-01

The ACME challenge Kanea can use decides what you have to arrange:

HTTP-01 (default)DNS-01
NeedsPort 80 reachable from the internet, and the name already resolving to the nodeAn RFC 2136 nameserver that accepts TSIG-signed updates
ConfigureNothing beyond acme.emailThe acme.dns01 block
Wildcard certificatesNoYes
Works on a private nodeNoYes

For HTTP-01 the edge serves the challenge path on :80. kanead first requests the challenge from its own edge, at acme.verify_url, and asks the CA to validate only once that succeeds.

For DNS-01, store the TSIG secret, then add the block and restart kanead:

kanea secret put shared/tsig < tsig.key
# /etc/kanea/kanea.hcl
acme {
  email = "ops@example.com"

  dns01 {
    server      = "ns1.example.com:53"
    zone        = "example.com"          # default: the challenge name's parent
    tsig_key    = "kanea-acme"
    tsig_secret = "secret:shared/tsig"   # a reference, never the literal
  }
}

tsig_secret is required whenever server is set, and it must be a secret: reference. kanead refuses to start otherwise, because unsigned updates would let anyone on the network answer a challenge.

RFC 2136 is the only DNS-01 method. It suits BIND, Knot and PowerDNS. A provider that offers only its own API needs a zone you run yourself, or a CNAME that delegates _acme-challenge into one.

When Kanea switches to wildcards

Certificates are per service until a node needs more than 20 of them. Past that, and only with DNS-01 configured, generated names collapse into one wildcard per project: *.shop.apps.example.com.

The threshold comes from Let's Encrypt's limit of 50 certificates per registered domain per week. Custom domains are never collapsed, because they belong to zones Kanea has no claim on.

Use your own certificates

Add one certificate block per certificate. A spec asks for a certificate by name and never names a path, so only someone who can edit the node config decides which private keys the node serves.

  1. Put the pair on the node

    The certificate file holds the leaf and its intermediates in PEM. Both paths must be absolute. kanead warns about a key that group or others can read.

  2. Add a certificate block

    The label is the name specs use. allow lists the projects that may claim the certificate and must not be empty. 

    # /etc/kanea/kanea.hcl
certificate "shop" {
  cert  = "/etc/kanea/tls/shop.crt"
  key   = "/etc/kanea/tls/shop.key"
  allow = ["shop"]
}

  3. Restart kanead

    Run sudo systemctl restart kanead. A new or changed block needs a restart, and a malformed block stops kanead from starting.

  4. Ask for it in the spec

    expose {
  domains = ["shop.example.com"]
  tls {
    mode = "provided"
    name = "shop"
  }
}

    Leave name out and Kanea picks any certificate the project is allowed that covers every domain of the route.

What a certificate covers is read from its own subject alternative names. There is no domain list to keep in step with the file.

A renewed pair is picked up without a restart. kanead checks the files every minute and compares their content, so a renewal tool that writes and renames works as it is.

A provided certificate that cannot be resolved leaves the service on plain HTTP. Kanea never substitutes a certificate from another source.

Private networks and homelabs

A node with no public name and no port 80 from the internet can still serve HTTPS. There are two routes. They differ in whether each device has to be told to trust a CA.

Use the node's own CA

  1. Point a wildcard at the node on your local resolver

    Create *.home.lan on a Pi-hole, a router or an internal BIND, and point it at the node's LAN address.

  2. Set the base domain and the default mode

    # /etc/kanea/kanea.hcl
base_domain = "home.lan"

tls {
  default_mode = "self-signed"
}

  3. Restart kanead and export the CA

    sudo systemctl restart kanead
kanea ca show > kanea-ca.crt

    The certificate goes to the file. Installation commands for each operating system are printed to the terminal, with the fingerprint to compare.

  4. Install the CA on each device

    Every service then answers at <service>.<project>.home.lan over HTTPS. This works offline and spends no rate limit.

The CA is named after tls.ca_name. Unset, it takes the base domain, and failing that the node's hostname. That name is what a device shows in its list of trusted authorities.

Use public certificates over DNS-01

If you own a public domain and can run RFC 2136 updates against it, configure DNS-01. The node then gets publicly trusted certificates for names that resolve only on your LAN, and devices need no setup.

Nothing has to be reachable from the internet, because the challenge is answered in DNS. The record still points at the node's LAN address.

Skip names altogether

Publish a port and reach the service at http://<node>:8096. That path needs no DNS and no certificate, and ip_restriction bounds who may use it. Which node ports a spec may publish is set by edge.publish.ports.
