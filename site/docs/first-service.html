Get started

Deploy your first service

Write a ten-line spec, preview it, apply it, and read the logs of the container it starts. You need a node that has been through kanea init.

Deploy from a spec

  1. Write the spec

    Save this as web.hcl:

    # web.hcl
spec_version = 1

project "demo" {}

service "web" {
  project = "demo"

  task "app" {
    image = "nginx:1.27-alpine"
  }
}

    A service needs a project and an image. Every other block in the spec reference is optional.

  2. Preview it

    kanea plan web.hcl

    kanea plan validates the spec and prints what an apply would create, change or destroy. It changes nothing on the node. 

    + create demo/web (count 1, image nginx:1.27-alpine)

Plan: 1 change(s) - 1 create.
Run `kanea run` to apply.

    A mistake in the spec is reported here with its file and line, and nothing else is printed.

  3. Apply it

    kanea run web.hcl

    kanea run prints the same preview and asks Apply? [Y/n]. Press Enter. It then waits up to 60 seconds for the container to start. 

    applied demo/web
demo-web-0 running (1/1)
1/1 allocs running

  4. Check that it is running

    kanea ps --project demo

    You get one row per alloc, which is one running copy of the service: 

    ALLOC       PROJECT  SERVICE  STATE    RESTARTS  IMAGE              AGE
demo-web-0  demo     web      running  0         nginx:1.27-alpine  12s

  5. Read its logs

    kanea logs -f demo/web

    The container's output streams to your terminal, starting with nginx's startup lines. Press Ctrl-C to stop following. Without -f the command prints what is there and exits.

The service is running but not reachable from outside the node, because the spec declares no expose block. Domains and HTTPS adds one.

Deploy without a file

For a quick try, name the image on the command line. This creates the same service as the spec above: 

kanea run --image nginx:1.27-alpine --name web --project demo

Move to a spec file when the service needs anything beyond an image and a count.

Read a plan

Run kanea plan before every apply. It prints one block per service and one row per resource that would be added, changed or removed. Rows marked (rolls allocs) replace running containers. The others take effect without a restart. 

$ kanea plan app.hcl
~ update shop/web
    image             web:v1 -> web:v2  (rolls allocs)
    env               + DB_URL, ~ LOG_LEVEL  (rolls allocs)
    volumes           + cache  s3:backups /var/cache rw 10 GiB budget  (rolls allocs)
    expose            + api.example.com  (tls acme, port 8080)

+ create shop/worker (count 2, image worker:v3)
    volumes           + queue  local /queue
    files             + /etc/app.conf  (412 B, content 3f2a1b9c, mode 0644)

Plan: 2 change(s) - 1 create, 1 update; 1 replace running allocs.
Run `kanea run` to apply.

kanea run renders its preview with the same code, so what you confirm is what the plan showed. --yes or -y skips the question. When stdin is not a terminal, as in a script or a CI job, the question is never asked.

A plan never prints an env value or the content of a config file, since either can carry a secret. It shows env keys, file paths and a short content digest, which is enough to see that something changed.

Remove a service

To remove one service:

kanea remove demo/web        # alias: rm; asks [y/N] on a terminal, --yes/-y skips

kanea stop demo/web --rm does the same, behind the same confirmation.

Deleting a service block from a spec and applying again does not remove the service. An apply only adds and changes, so applying web.hcl cannot delete what another file declares. To make the spec authoritative for its projects, add --remove-orphans: 

kanea plan --remove-orphans app.hcl   # `- destroy` lines for what would go
kanea run  --remove-orphans app.hcl

This removes every service in the file's projects that the file does not declare. Projects without a project block in the file are left alone. The flag is refused together with a selector or --image, because neither sends a whole project.

Removing a service deletes its containers, alloc records, VIP, routes and mounts. Volume data is never deleted, so a service removed by mistake comes back with its data when you apply it again. Its log files stay on disk too: kanea logs --previous demo/web reads what it last wrote.
