Reference

Spec reference

Every block and field a spec accepts, the rules it is checked against, and one complete file. To write and deploy your first one, follow Deploy your first service.

Specs are HCL v2. Every rule on this page is enforced when the file is parsed, and errors carry file, line and column. Run kanea plan to see them before anything changes.

Top level

A spec file holds spec_version and any number of the blocks below. Files applied together are parsed as one set and file order is irrelevant: a service may reference a project declared in another file.

FieldTypeNotes
spec_versionnumberCurrently 1. Later spec revisions are gated on this field.
project "<name>"blockZero or more. The name is a DNS-1123 label.
service "<name>"blockZero or more.
function "<name>"blockZero or more. A wasm module run as a service.
storage "<name>"blockZero or more. A named volume backend.
variablesblockOptional. Shared values the rest of the spec references as ${name}.
env_group "<name>"blockZero or more. An environment that services opt into with env_from.

variables

Declare a value once and reference it anywhere as ${name}. Where HCL takes an expression, such as count, use the bare name. 

variables {
  domain   = "shop.example.com"
  replicas = 3
}

service "web" {
  project = "shop"
  count   = replicas
  expose {
    domains = ["${domain}", "www.${domain}"]
  }
}
RuleDetail
Value typesString, number or bool. A list or object is refused by name.
PrecedenceLowest to highest: the node's variables stanza, the spec's block, pipeline values such as ${GIT_SHA_SHORT}.
References inside a valueA value may reference node variables and built-ins. It may not reference another spec variable.
Reserved namesGIT_SHA, GIT_SHA_SHORT, GIT_BRANCH, KANEA_PROJECT, service and secret cannot be declared.
DuplicatesDeclaring the same name twice across a spec's files is an error.
Variables are not secrets

The node's stanza is served to any signed-in caller over GET /v1/vars. Keep credentials as secret: references. A variable whose value contains such a reference is fine.

A named group of services. It is the isolation boundary for network policy, secrets, containerd namespaces and DNS.

A synced spec that declares a different project is refused. Without that boundary, push access to one repository would be control of every service on the node.

The webhook never deploys from the request body. It marks the project dirty, and the sync loop re-reads the source with Kanea's own credential. A forged body can only make a legitimate sync happen sooner.

storage

A named volume backend. Services mount it by name with a volume block. The setup guides for each type are on Volumes and host access.

hardening

Set hardening = "restricted" for the strong profile. The task must then declare a non-zero user, it runs with no capabilities, and a capabilities list beside it is refused.

Init steps are unaffected. The usual shape is a root init step that fixes ownership and exits, followed by a restricted task.

depends_on and service references

A service does not start until every dependency is healthy. Dependencies come from depends_on and from every ${service.…} reference, which creates the same edge implicitly.

  • References are same-project only. The referenced service and port must exist in the applied set.
  • A dependency cycle is rejected, and the diagnostic shows the cycle.
  • If a dependency degrades after start, dependents keep running and an event is emitted.

capabilities

Every container starts from a baseline set. The list you declare is added to it. Start the list with "none" to drop the baseline: ["none"] grants nothing, and ["none", "CAP_NET_RAW"] grants exactly one capability.

SetCapabilities
BaselineCHOWN, DAC_OVERRIDE, FOWNER, FSETID, KILL, SETGID, SETUID
May be addedSETPCAP, SETFCAP, NET_BIND_SERVICE, NET_RAW, SYS_CHROOT, MKNOD, AUDIT_WRITE
Refused at parseSYS_ADMIN, SYS_MODULE, SYS_RAWIO, SYS_PTRACE, SYS_BOOT, SYS_TIME, SYS_NICE, SYS_RESOURCE, DAC_READ_SEARCH, BPF, PERFMON, MAC_ADMIN, MAC_OVERRIDE, NET_ADMIN

Binding port 80 inside a container needs no capability. SETFCAP has one caveat: a file capability set on a binary in a read-write host volume stays on the host file.

init

An init block is setup that must finish before the task starts: a schema migration, a chown of a new volume, a config render. A service may declare any number. They run in declaration order, one at a time, and the task is created only after the last exits zero. 

service "api" {
  # The chown happens in the root init step, so the task itself
  # runs as 999 with no capabilities at all.
  hardening = "restricted"

  # Runs as root to fix a directory the task will own as 999.
  init "fix-perms" {
    image        = "busybox:1.36"
    command      = ["chown", "-R", "999:999", "/data"]
    capabilities = ["CAP_CHOWN"]
    timeout      = "1m"
  }

  init "migrate" {
    image   = "registry.example.com/shop/api-migrate:1.4"
    command = ["/bin/migrate", "up"]

    env = {
      DATABASE_URL = "secret:shop/database-url"
      DATABASE_HOST = "${service.postgres.host}"   # a real dependency edge
    }

    timeout = "5m"
  }

  task "app" {
    image = "registry.example.com/shop/api:1.4"
    user { uid = 999 }
  }
}
FieldTypeNotes
imagestringRequired. An init step has no build block.
command, argslist(string)Same rules as on a task.
envmapIts own. secret: references and ${service.…} work as on a task.
resourcesblockIts own. An omitted limit is unbounded.
userblockIts own numeric identity, independent of the task's.
capabilitieslist(string)Same baseline and permitted set as a task.
registry_auth_refsecret refThis step's pull credential.
pull_policystringif-not-present or never. always is task-only.
timeoutdurationBounds this step. Omit it for no timeout. The kill lands within one reconcile pass after it expires.

Each step shares the alloc's network namespace, volumes, files and secrets. So ${service.…} and internal DNS resolve as they do for the task, which makes a wait-for-database step possible. Nothing else is inherited from task.

An init block has no device, socket, health_check, expose, scaling, count, depends_on, network or build field. Step names are DNS-1123 labels, unique within a service.

When the sequence runs

The sequence runs once per service, not once per alloc. The first alloc (index 0) runs it. Every other alloc of the service waits for it, then starts with no sequence of its own. So count = 3 means three replicas and one migration.

  • The sequence re-runs from the first step whenever the first alloc is created: a deploy, a spec change, a crash restart. A half-run sequence is never resumed, so steps must be idempotent.
  • On a deploy the other allocs wait again until the first alloc has finished the sequence for the new spec.
  • A waiting alloc says what it is waiting for in kanea ps.
  • If the first alloc fails its sequence, the service does not start, and the wait names the failed step.
Per-alloc volumes are prepared for the first alloc only

Local storage gives each alloc its own directory. A step that prepares this alloc's volume, such as a chown, prepares the first alloc's and no other. kanea plan warns when a service with count > 1 declares both init steps and a local volume. Steps that work on shared state are unaffected.

Logs and failures

Read a step's output with kanea logs shop/api -c migrate. Attempts append to one transcript per alloc. Each attempt opens with a separator line that names the step and its start time.

What happenedResult
The step ran and exited non-zero, or outlived its timeoutThe alloc fails and one restart attempt is spent. A broken migration stops after attempts.
The step could not be pulled or createdRetried every reconcile pass. No attempt is spent, because nothing ran.

env_group

An env_group declares environment variables once. A service takes them with env_from. Unlike variables, which substitutes text you still write in every service, a group is injected. 

env_group "common" {
  LOG_LEVEL = "info"
  REGION    = "eu-central-1"
}

env_group "db" {
  DATABASE_HOST = "${service.postgres.host}"
  DATABASE_URL  = "secret:shop/database-url"
}

service "api" {
  project  = "shop"
  env_from = ["common", "db"]

  task "app" {
    image = "registry.example.com/shop/api:1.4"
    env   = { LOG_LEVEL = "debug" }   # the service's own env wins
  }
}
  • Groups apply in the order env_from lists them. Each container's own env wins over all of them, for the task and for every init step.
  • A group name is a DNS-1123 label, unique across the spec's files.
  • Taking a group is opt-in per service. Environment is baked into a container, so changing a shared value rolls every service that takes it.
A group is evaluated once per service that takes it

${service.…} is scoped to a project. The db group above resolves to postgres.shop.kanea for a service in shop, and to a different address in another project. The dependency edge lands on the taking service, which is why it starts after postgres.

A secret: in a group is checked against every consumer. A group that carries shop's credential is refused for a service in another project.

file

A file block places content in the container. Use it instead of baking a config file into an image or mounting a host volume to carry one. 

service "web" {
  file "nginx" {
    path   = "/etc/nginx/conf.d/app.conf"
    source = "./nginx.conf"        # read at parse, embedded in the record
  }

  file "pgpass" {
    path    = "/etc/app/pgpass"
    mode    = "0400"
    content = "db:5432:app:${secret.shop[\"database-password\"]}"
  }
}

content is an ordinary HCL string, so a whole config file fits in a heredoc. 

file "app-config" {
  path    = "/etc/app/config.yaml"
  content = <<-EOT
    server:
      addr: ":8080"
      upstream: "${service.api.host}:${service.api.port.http}"
    database:
      dsn: "postgres://app:${secret.shop[\"database-password\"]}@db:5432/app"
    log:
      # a literal dollar-brace the app expands itself
      format: "$${level} $${msg}"
  EOT
}
FieldTypeNotes
pathstringRequired. Absolute, clean and free of ... Refused under /dev, /proc, /sys, at /etc/resolv.conf, and where a volume, socket or another file mounts.
contentstringInline. ${service.…} and ${secret.…} interpolate. Write a literal dollar-brace as $${…}, which is HCL's escape.
sourcestringA relative path beside the spec, read at parse and embedded. No symlink in any component. Mutually exclusive with content.
modestringOctal. Default 0644, or 0400 for a file that interpolates a secret. An execute bit is refused.
  • Give exactly one of content and source.
  • Files mount read-only with nosuid,noexec,nodev, after volumes. A file at a path inside a volume wins.
  • Init steps see the files too.
  • Content is capped at 64 KiB per file and 128 KiB per service, because the service record is replicated in full on every deploy.
  • Editing a file's content rolls the service.
A secret in a file never enters Kanea's state

${secret.<scope>.<name>} resolves to an opaque placeholder at parse. The stored record keeps the reference, and the node substitutes the value when it creates the container. The credential is absent from the state database, from backups and from GET /v1/services.

A file that carries a secret is written 0400 on a tmpfs of its own, owned by the workload's user. A rotation lands at the next replacement. Use the bracket form for names that are not bare identifiers: ${secret.shop["database-password"]}.

Where source can be read

kanea run reads it from the directory beside the spec. A synced repository reads it from the commit. The dashboard's spec editor and the MCP spec tools parse text inside kanead, so they refuse source and want content. Reading a path there would be a root file read on behalf of whoever is signed in.

pull_policy

pull_policy says where an image may come from. Set it on a task or an init block.

ValueMeaning
if-not-presentUse the node's content store and pull only what is absent. The default.
neverUse the content store or fail the alloc, naming the policy. For air-gapped nodes and nodes with preloaded images.
alwaysRe-resolve the tag and, when the digest has moved, pin it and roll every replica through the update policy. Task only.

Omit the field to take the node's default, which the operator sets with images.pull_policy in the node config.

always does not re-pull at every container creation. That would let two replicas of one spec run different bytes. It turns on update { auto = true } and inherits its refusals: no build block, a tag instead of a digest, and no update { auto = false } beside it.

device and socket

Both blocks name a grant and never a path. The operator defines grants in the node config and the spec asks for one by name. A spec has no field for a device path, so it cannot request /dev/mem. 

service "jellyfin" {
  task "app" {
    image = "jellyfin:10.9"

    device "dri" {
      grant = "gpu"          # defined by the operator, not here
    }
  }
}

service "watchtower" {
  task "app" {
    image = "watchtower:1.7"

    socket "runtime" {
      grant      = "containerd"
      mount_path = "/var/run/docker.sock"
    }
  }
}
FieldTypeNotes
grantstringRequired on both blocks. Names a device or socket grant in the node config. A DNS-1123 label.
mount_pathstringsocket only, required. Where the socket appears in the container. A device appears at its host path.
read_onlyboolsocket only. Restricts the filesystem entry, not the protocol spoken over it.

mount_path is absolute, clean and free of ... It may not sit under /dev, /proc or /sys, and may not collide with another socket or a volume. Block labels are unique within a task.

The node checks the grant at every alloc start. It refuses a grant it does not have, a grant whose allow list does not name the project, and a device path that is not a device. A refused grant fails the alloc. To define grants, follow Devices and sockets.

A socket grant is root on the node

A container that holds the runtime socket can start other containers without the hardening defaults. Nothing contains that. The only control is the grant itself: it lives in a file no spec author can write, and it names the projects allowed to use it.

network

network {
  port "http" { container = 8096 }

  publish "http" {
    host = 8096                                  # http://<node>:8096
    mode = "http"                                # "http" (default) | "tcp" | "udp"
    ip_restriction { allow = ["192.168.0.0/16"] }
  }

  policy { allow_from = ["analytics/collector"] }
}

port "<name>"

FieldTypeDefaultNotes
containernumber-Required. The port inside the container.
protocolstringtcptcp or udp.

The name is what expose, publish and health_check refer to, and what ${service.x.port.<name>} resolves.

publish "<port name>"

A node port the edge binds for this service, with or without a domain. The label names a declared port. There is no field for a container port number, so a published port cannot reach an undeclared one.

FieldTypeDefaultNotes
hostnumber-Required. The node port, 1-65535.
modestringhttphttp, tcp or udp.
max_connsnumbernode'stcp only. Bounds live connections on this listener. Refused on an http listener.
ip_restrictionblock-Allowed in every mode.
rate_limit, headersblock-http only. On a tcp or udp listener they are a plan error.
ModeBehaviour
httpThe edge proxies HTTP and applies the full middleware chain.
tcpRelays bytes, for Postgres or a game server. The upstream sees the edge's address, so ip_restriction, enforced at accept time, is the only client control.
udpRelays datagrams. One session per client source address, pinned to a backend so a conversation survives an edge restart.

UDP source addresses can be forged, so two limits apply. A source IP may hold at most 8 live sessions. A session sends at most 4 KiB back until the client sends a second datagram. Refusals are counted in kanea_edge_udp_refused_total.

The node decides which ports a spec may claim, with edge.publish.ports. The default is 1024-65535, so a repository cannot take port 22. Ports 80, 443 and the control-plane ports are always reserved.

policy

allow_from lists the peers in other projects that may reach this service. Each entry is a full "<project>/<service>".

  • An entry only adds reachability. It cannot weaken the default, which denies traffic from other projects.
  • There is no wildcard: "analytics/*" is a parse error.
  • Same-project entries are accepted and redundant.

expose

An expose block is one public route through the edge: domains, a port, TLS and middleware. The block may repeat, so one service can serve its UI and its API on different names and ports.

FieldTypeNotes
domainslist(string)Omitted, the route is <service>.<project>.<base_domain>, from the node's base_domain. Only the first block may omit it.
portstringThe declared network { port } the route proxies to. Omitted, the port named http, or the only declared port.
protocolstringhttp (default) or grpc.
tlsblockmode, name.
authblockRequires a credential on every request.
ip_restrictionblockallow, deny: lists of CIDRs. An empty allow means everyone. Deny wins.
rate_limitblockrequests and window (required), per, burst. per is ip, service or header:<name>.
headersblockrequest_set, request_remove, response_set, response_remove.
  • A service may be exposed only if it declares a port. Naming an undeclared or udp port is a plan error.
  • Every domain is validated as a hostname. No two services may claim the same one, counting generated names.
  • Blocks that declare auth must declare the same auth.

Middleware order

The chain runs in a fixed order, whatever order the blocks are declared in:

Host match → IP allow/deny → rate limit → auth → header transforms → upstream
You cannot touch X-Forwarded-*

The headers block rejects any attempt to set or remove the X-Forwarded-* headers or the hop-by-hop headers. They carry the client identity that IP restriction, rate limiting and the audit log rely on.

tls

FieldTypeNotes
modestringacme, self-signed, provided or plaintext. An unknown value is an error.
namestringWith provided: selects one of the node's certificate blocks. A DNS-1123 label.

Omit the block and the node decides, from tls.default_mode. A mode names a certificate source and never a path. The guide is Domains and HTTPS.

protocol

protocol = "grpc" makes the edge dial the upstream over cleartext HTTP/2. The route then uses the port named grpc when one is declared. It is refused beside tls { mode = "plaintext" } and beside an http-mode publish of the same port.

  domains = ["api.example.com"]

health_check

health_check "http" {
  type     = "http"     # http | tcp | exec
  path     = "/healthz" # http only
  port     = "http"     # port name, required for http and tcp
  interval = "10s"
  timeout  = "2s"

}
FieldTypeDefaultNotes

Only a probe writes alloc health. A service with no health_check block has every alloc unhealthy, and Kanea treats it as "no check configured" instead of "failing". Declare one if you rely on min_healthy or on dependents waiting for this service.

Ownership

Omitted, uid, gid and mode inherit from task.user, and an owned volume takes mode 0700. With no user block the volume stays root-owned, 0750. Set uid = 0 to ask for root on purpose.

Storage typeOwnership fields
localApplied: the directory is chowned and chmodded.
smb, s3Applied as mount options.
hostPlan error. The directory is the operator's.
nfsPlan error. Ownership belongs to the NFS server.

Size budget

size is a budget and nothing enforces it. Kanea measures the volume on a slow background schedule and shows usage in kanea volume list. It emits volume.over_budget when usage crosses the budget and volume.under_budget when it comes back.

  • On an s3 volume, size is a plan error: that driver is never measured.
  • Changing size does not redeploy the service.

update and restart

  strategy     = "rolling"   # rolling | replace
  max_parallel = 1
  min_healthy  = "30s"

  interval = "6h"            # how often to re-resolve it; minimum 5m
  deadline = "10m"           # how long a new digest has to prove itself

  attempts = 5
  backoff  = "10s,30s,1m,5m"

intervalduration6hHow often the tag is re-resolved. Minimum 5m.
deadlineduration10mHow long a new digest has to converge before it is reverted.

With auto = true, Kanea re-resolves the declared tag and pins the digest behind it when it moves. The tag stays in the spec and the digest is what runs. The roll is an ordinary deploy, gated by max_parallel, min_healthy and the health check.

  • If the new digest does not converge within deadline, the previous digest is pinned again. Converged means healthy where a health check exists, and running without crash-looping where none does.
  • Re-applying the spec forces a re-check within about a minute. Push new bytes under the same tag, then kanea run.
  • Editing image costs one rolling deploy: the apply resolves the new tag's digest in the same write. If the registry is unreachable, the watcher pins the digest later with a second roll.
  • The pinned digest survives a re-apply. Editing image or turning auto off hands control back to the spec.
  • It is refused on an image that is already a digest and on a service with a build block.
  • Private registries need task.registry_auth_ref.
  • Outcomes emit image.updated and image.update_failed.

restart

FieldTypeDefaultNotes
attemptsnumber5Crash restarts before the alloc is marked failed. Zero means the default.
backoffstringbuilt-in scheduleComma-separated positive durations. Each restart waits the next entry and the last entry repeats.
  • An alloc that exhausts attempts is failed and left alone until a deploy or kanea restart. Either resets the count.
  • Only crashes kanead watched are counted. An alloc found stopped at startup, after a reboot or power loss, is recovered at once without spending an attempt.
  • An alloc already marked failed stays failed across a reboot.
  • Changing the restart block does not roll healthy allocs.

build

build {
  context           = "./web"
  dockerfile        = "Containerfile"   # optional; auto-detected when omitted
  target            = "registry.example.com/shop/web"   # optional
  tag               = "${GIT_SHA_SHORT}"
  cache_repo        = "registry.example.com/shop/web-cache"
  registry_auth_ref = "secret:shop/registry"
}
FieldTypeNotes
contextstringRequired. A directory inside the checkout. Absolute paths, .. and symlinks are refused.
dockerfilestringA path inside the checkout. Omitted, Containerfile is used, then Dockerfile.
targetstringImage reference to push to. Omitted, the node's internal registry is used.
tagstringMay not contain a comma, = or whitespace.
cache_repostringImage reference for the build cache. May not point at the internal registry.
registry_auth_refsecret refPush credential. Written as a config.json for the build and kept out of the build context.
  • Builds run on rootless BuildKit.
  • With no target, the node composes <registry>/<project>/<service> on its loopback-only build registry. So build { context = "." } is a complete build configuration with no external registry and no push credential.
  • The operator sets the registry and BuildKit addresses in the node's builds stanza. The registry defaults to 127.0.0.1:5100.
  • A service with a build block and no task.image is valid. It waits until the first build pins a digest. When both are present, the built digest wins.
  • Builds run one at a time. When the queue is full a new build is refused, and shutdown cancels what is still waiting.

function

A function is a wasm module run as a service. It serves wasi-http on the wasmtime shim that kanea init installs. It deploys, rolls and scales like any service, and its triggers decide what calls it. 

function "resize-avatar" {
  project = "shop"
  module  = "registry.example.com/shop/resize-avatar:v3"  # FROM scratch + module

  trigger "http" {}                                # its domain name, or the edge's
                                                   # functions port: /<project>/<function>/
  trigger "event" { on = ["deploy.failed"] }       # POSTed matching events
  trigger "cron"  { schedule = "0 3 * * *" }       # five fields, UTC

  resources { memory = 64 }                        # a real cgroup cap
}
FieldTypeDefaultNotes
project, description, count, depends_on, env--As on a service and its task.
modulestring-An OCI image whose entrypoint is the wasm module. Optional when a build block is present.
portnumber8080The port the module listens on.
resourcesblockcpu = 100, memory = 64Enforced by cgroups.
registry_auth_refsecret ref-Pull credential for the module image.
signing_refsecret ref-Key that signs every event and cron POST with an HMAC in X-Kanea-Signature.
trigger "<kind>"block-At least one is required.
build, health_check, update, restartblock-As on a service.

A function has no volumes, devices, sockets, capabilities, user, command or args. The sandbox cannot honour them, so the spec cannot declare them. kanea functions list shows triggers, invocation rate and status.

trigger

KindFieldsNotes
httpdomains, tls, ip_restriction, rate_limit, headers, authThe same fields and rules as expose, without port or protocol.
eventon, pathon holds event globs, validated like notifications.on. Patterns matching function.* are refused.
cronschedule, pathA five-field cron expression, evaluated in UTC.

path is where the event or cron POST lands. It is a normalised absolute path and defaults to /. No trigger has a field for a target URL: kanead always calls the function's own address.

Interpolation

Several forms of ${…} appear in a spec. They resolve at different times.

FormResolvedNotes
${VAR}Parse timeFrom the spec's variables block, the node's variables stanza, and built-ins such as KANEA_PROJECT.
${GIT_SHA_SHORT}Checkout timeSurvives parsing as a literal reference. Its value exists only once a commit is checked out.
${service.<n>.host}Alloc startBecomes <n>.<project>.kanea. A DNS name, never an IP.
${service.<n>.port.<p>}Alloc startThe named port's frontend port.
${secret.<scope>.<name>}Container createInside a file block's content only.
secret:<project>/<name>Alloc startA reference, not interpolation. In env, the variable holds the path of a read-only tmpfs file that contains the value.
secret-env:<project>/<name>Alloc startenv only. The variable holds the value itself. Weaker: the value is visible in the process environment.

A secret reference may name the service's own project or shared/, and nothing else. Managing secrets is covered in Secrets.

Remove a service from a spec

Deleting a service block and re-applying does not stop the service. An apply replaces the desired state of the services it names and leaves everything else alone. Remove a service with one of these two commands.

One serviceEverything a spec dropped
Commandkanea remove shop/webkanea run --remove-orphans app.hcl
Scopethe service you namethe spec's project blocks
Dry run-kanea plan --remove-orphans app.hcl

--remove-orphans makes the spec authoritative for every project it declares a project block for. Anything stored in one of them that the file does not declare is deleted, in the same atomic batch as the applies. Projects the spec does not mention are never touched. 

$ kanea plan --remove-orphans app.hcl
- destroy shop/legacy-worker (count 1, image legacy:v3)
    volumes           - scratch  local /scratch rw
                        (the mount goes; the volume's data is NOT deleted)

~ update shop/web
    image             web:v1 -> web:v2  (rolls allocs)

Plan: 2 change(s) - 1 update, 1 destroy; 1 replace running allocs.
Run `kanea run` to apply.

$ kanea run --remove-orphans app.hcl
[the same block]

Apply? [Y/n]
applied shop/web
removed shop/legacy-worker

1 service(s) removed. Volume data was not deleted.
Refused with a selector, and with --image

kanea run --remove-orphans app.hcl shop/web is refused. A selector sends part of the spec, so the apply cannot speak for a whole project. --image is refused too: it declares one service and no project.

Put flags before file arguments.

What a prune destroys, and what survives

GoesStays
The containers, and the alloc records behind kanea psVolume data, local and network
The service's virtual IP, which another service may then takeCertificates, including issued ACME ones
Its routes, and its network volume mountsSecrets under the project
The restart generation and any pinned image digestIts internal datapath id, which is keyed by name
  • Volume data is never deleted. Re-apply a service pruned by mistake and it comes back with its data.
  • A prune frees no disk. Reclaim it by hand with rm under the volume directory.
  • Each removal emits service.removed and is named in the audit log.
  • A GitOps sync applies additively. A service removed from a synced spec keeps running until someone prunes or stops it.

Full example

One project with a database and a web frontend. This file parses and validates against Kanea's own parser.

shop.hcl
# shop.hcl: everything for one project
spec_version = 1

project "shop" {
  description = "E-commerce storefront stack"

  git {
    url      = "https://github.com/example/shop-deploy.git"
    branch   = "main"
    path     = ".kanea/"
    auth_ref = "secret:shop/github-deploy-key"
  }

  notifications {
    slack { url_ref = "secret:shop/slack-webhook" }
    on       = ["deploy.failed", "service.unhealthy", "scale.*"]
    severity = "warning"
  }
}

storage "local-ssd" {
  type = "local"
}

service "postgres" {
  project = "shop"

  task "db" {
    image = "postgres:16-alpine"
    env = {
      POSTGRES_PASSWORD = "secret:shop/postgres-password"
    }
    resources {
      cpu    = 1000
      memory = 1024
    }
  }

  network {
    port "pg" { container = 5432 }
  }

  volume "data" {
    storage    = "local-ssd"
    mount_path = "/var/lib/postgresql/data"
  }

  health_check "tcp" {
    type     = "tcp"
    port     = "pg"
    interval = "10s"
  }
}

service "web" {
  project     = "shop"
  description = "Storefront frontend"
  count       = 3
  depends_on  = ["postgres"]

  build {
    # No target: the node's internal registry builds, pushes and deploys
    # this service without any external registry.
    context = "./web"
  }

  task "app" {
    image = "registry.example.com/shop/web:latest"

    env = {
      NODE_ENV      = "production"
      DATABASE_URL  = "secret:shop/database-url"
      DATABASE_HOST = "${service.postgres.host}"
      DATABASE_PORT = "${service.postgres.port.pg}"
    }

    resources {
      cpu    = 500
      memory = 512
    }
  }

  network {
    port "http" { container = 3000 }
  }

  expose {
    domains = ["shop.example.com", "www.shop.example.com"]
    tls { mode = "acme" }

    ip_restriction {
      deny = ["198.51.100.7/32"]
    }

    rate_limit {
      requests = 100
      window   = "1m"
      per      = "ip"
      burst    = 20
    }

    headers {
      response_set    = { Strict-Transport-Security = "max-age=63072000; includeSubDomains" }
      response_remove = ["Server", "X-Powered-By"]
    }
  }

  health_check "http" {
    type     = "http"
    path     = "/healthz"
    port     = "http"
    interval = "10s"
    timeout  = "2s"
    failures = 3
  }

  scaling {
    min = 2
    max = 10
    metric "cpu" { target = 70 }
    metric "rps" { target = 500 }
    cooldown = "2m"
  }

  update {
    strategy     = "rolling"
    max_parallel = 1
    min_healthy  = "30s"
  }

  restart {
    attempts = 5
    backoff  = "10s,30s,1m,5m"
  }
}
