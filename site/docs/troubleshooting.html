Guides

Troubleshooting

Find what is wrong by looking at the workload first, then the daemons under it, then the node. The checks in the first three sections are read-only and safe on a live node.

Check services

Start with what Kanea believes is true:

kanea ps -a                  # every alloc, including stopped services and pending slots
kanea status shop/web        # health, recent events, current and desired counts
kanea describe shop/web      # spec, routes, volumes, allocs, stats and events

Three columns of kanea ps carry most of the signal for an alloc:

ColumnReadingMeans
StatependingThe slot is not created yet. Usually an image is still pulling, or a dependency is not healthy.
Health-The service declares no health check. It is reported as running or not, never as unhealthy.
RestartsclimbingA crash loop.
Restartsstopped climbingThe restart budget is spent and the alloc is failed. See A service is crash-looping.

A node reboot moves no counter: allocs found stopped at boot come back without spending the budget.

Check the daemons

A standard install runs four units:

systemctl status kanead kanea-edge kanea-containerd kanea-buildkit
UnitDoesWhile it is down
kaneadThe control plane: API, dashboard, deploys, scaling, certificates.Workloads and ingress keep running. Nothing changes: no deploys, no scaling, no renewals.
kanea-edgeThe ingress proxy. It does not depend on kanead.No traffic from outside reaches your services.
kanea-containerdKanea's own containerd, at /run/kanea/containerd.sock.Running containers keep running. Nothing can be created or probed.
kanea-buildkitThe rootless build daemon.Builds fail. Everything else works.

The edge serves the last route table it read from disk, whether or not kanead is up. kanea-containerd is absent on a node set up with kanea init --containerd external.

Check the node

kanea doctor verifies the node and changes nothing. It checks the kernel and cgroup v2, the host components against their pinned versions, bpffs, the subnets, IP forwarding, the host firewall, the build daemon, disk space and clock sync.

A check the current user may not perform reads SKIP, never FAIL. Run it with sudo for the full set.

Read logs

Workload logs

kanea logs shop/web -f               # merged across allocs, follow
kanea logs shop/web --tail=200       # the last 200 lines first
kanea logs shop/web --alloc=<id>     # one alloc only (ids from kanea ps)
kanea logs shop/web -c migrate       # an init step's log, by its block name
kanea logs shop/web --previous       # what a stopped or removed service left on disk

On disk there is one file per alloc, <alloc-id>.log, under /var/log/kanea/allocs/. The directory is alloc_log_dir in the node config. A replaced alloc starts a new file under its new id.

Log collection never blocks the workload. Under a burst of output Kanea drops lines and counts the drops, so missing lines under load are expected.

Daemon logs

The daemons log to stderr, which under systemd is the journal:

journalctl -u kanead -e              # control plane: reconciler, deploys, certificates, backups
journalctl -u kanea-edge -e          # ingress: TLS, routing, published ports
journalctl -u kanea-containerd -e    # runtime: image pulls, task create failures
journalctl -u kanea-buildkit -e      # the build daemon

journalctl -u kanead -f --since "15 min ago"

A deploy that goes wrong is usually explained in kanead's journal. A task that will not create at all, for a missing shim or an ungranted device, is often explained in kanea-containerd's.

Build logs

kanea build shop/web --follow streams a build live and kanea project builds shop lists past runs. Each run also has a file under /var/lib/kanea/builds/, which is builds.log_dir.

Slices and resources

Everything Kanea runs sits in one of two cgroup slices:

SliceHoldsGuarantee
kanea.sliceThe four units aboveA memory floor, MemoryMin, 256 MiB by default. Raise it with kanea init --reserve on a node that runs builds.
kanea-workloads.sliceEvery allocA shared ceiling of total RAM minus that reserve.

Architecture explains the design.

systemctl status kanea.slice             # the control plane, with its live memory number
systemctl status kanea-workloads.slice   # every alloc as a child cgroup
systemd-cgls kanea-workloads.slice       # the tree, one cgroup per alloc
systemd-cgtop                            # live CPU and memory per slice

kanead computes the ceiling at startup from the node's memory. Read both values from the cgroup filesystem: 

cat /sys/fs/cgroup/kanea.slice/memory.min             # the floor
cat /sys/fs/cgroup/kanea-workloads.slice/memory.max   # the ceiling
cat /sys/fs/cgroup/kanea-workloads.slice/memory.current

Each alloc has its own cgroup one level down, at /sys/fs/cgroup/kanea-workloads.slice/<alloc>/, with memory.max, memory.current and cpu.max. A declared resources limit is enforced there. An omitted one reads max: unbounded within the shared ceiling.

kanead was OOM-killed

The floor and the OOM score adjustments live in the unit files. A kanead started outside its unit runs without them, and under memory pressure the kernel may pick it.

Check that systemctl status kanead shows it inside kanea.slice, then run journalctl -k | grep -i oom to see what the kernel chose.

Common situations

kanead will not start after editing kanea.hcl

kanead reads /etc/kanea/kanea.hcl, the node config, once at startup and refuses to start on a file it cannot accept. Meanwhile your workloads keep running and the edge keeps serving the last route table it read.

  1. Read the refusal

    Run journalctl -u kanead -n 30. The last error line names the cause. kanea doctor reports the same error without restarting anything.

  2. Fix the cause

    The messageCauseFix
    Names the file and a lineA syntax error, or an attribute the stanza does not have.Correct that line. Node config lists every attribute.
    Says the file is group- or world-writable, has the wrong owner, or is not a regular fileOwnership or mode. kanead refuses a file another user could have written.sudo chown root:root /etc/kanea/kanea.hcl && sudo chmod 0644 /etc/kanea/kanea.hcl
    Names an attribute, such as bind.api_tlsA value refused by its own check: two attributes that contradict, a duration that does not parse, overlapping subnets.Change the value the message names.

  3. Start kanead again

    Run sudo systemctl restart kanead. systemctl is-active kanead prints active.

Leave kanea-edge running while the file is broken. The edge reads only the bind and edge stanzas, but a syntax error anywhere in the file stops it at its next start too.

Both daemons also refuse any command-line argument. The journal then shows kanea agent takes no arguments, or the same for kanea edge, and points at sudo kanea config migrate.

If the journal shows that message, a unit file still passes flags. Migrating from flags has the steps.

An edit to kanea.hcl has no effect

  • The file is read once. Restart kanead, and kanea-edge too for bind.edge_* and edge attributes.
  • A misspelled stanza name is a warning, and the stanza is skipped. Run journalctl -u kanead -b -p warning: the warning names it.
  • A backup destination saved in the dashboard wins over the backup stanza. See Back up a node.

A service is crash-looping

Read kanea logs shop/web for the reason. Once the restart budget is spent, the alloc is failed and left alone.

Fix the cause and deploy, or run kanea restart shop/web. Either one starts a fresh budget. Only crashes kanead watched count against it: after a power loss, stopped allocs come back on their own.

A deploy did nothing

Re-running an unchanged spec is a no-op. Run kanea plan to see the diff kanead would apply. An empty diff means the spec is what is running.

The site is unreachable but the service is healthy

  1. kanea describe shop/web shows the routes the service declares.
  2. systemctl status kanea-edge shows whether the edge is up.
  3. The edge reads its routes from /run/kanea-edge/routes.json. A route missing from that file is a publishing problem: read kanead's journal. A route present in it is a proxying problem: read the edge's.

Browsers show a certificate error

A domain whose certificate is not issued yet refuses the TLS handshake. A provided certificate that cannot be resolved leaves the route on plain HTTP. In neither case does Kanea substitute a weaker certificate.

kanead's journal has the ACME or resolution failure. Domains and HTTPS lists what issuance needs.

The dashboard fails the TLS handshake

Check the port first. The dashboard answers on the port of bind.api_addr, as in https://<name>:8600. The bare name goes to port 443, which is the edge.

On a node with no exposed services the edge holds no certificates. The handshake then fails with SSL_ERROR_INTERNAL_ERROR_ALERT in Firefox, where you might expect a 404.

If the port is right, the certificate may not have arrived yet. The listener refuses the handshake until it does. Check with journalctl -u kanead | grep 'api listener certificate installed'. Reach the dashboard covers the modes.

A service has no public name, or the name does not resolve

SymptomCauseFix
kanea describe shows no domainThe service lists no domains and the node has no base domain.Set base_domain in the node config and restart kanead.
The name does not resolveNo DNS record points at the node.Create the record. A wildcard covers every service.
It resolves but no certificate arrivesThe record did not point at the node before issuance, or acme.email is unset.Fix the record, and set acme.email.

Containers cannot reach each other, or DNS fails inside them

Run kanea doctor first. A host firewall with a default-deny policy, such as ufw, firewalld or docker's FORWARD drop, blocks two things workloads need:

  • Alloc traffic crosses the forward hook on its way out.
  • A query to the internal resolver at 10.244.0.1:53 crosses the input hook, because it is a new inbound connection to the host.

The host's own dig keeps working, which makes this look like broken Kanea DNS. kanea firewall prints the rules this node needs for the detected manager. Add --all for every manager, or --manager ufw for one. It prints and never applies.

A cross-project call resolves but times out

That is policy. Names resolve for everyone, and traffic between projects is denied by default. Add allow_from naming the caller on the service being called. A dropped packet shows as a timeout, not a refusal.

The autoscaler stopped scaling

Its circuit breaker trips after repeated failed actions. The journal and the dashboard say so, and /v1/metrics reports kanea_circuit_breaker_open.

The trip survives a restart of kanead, so fix the cause. kanea scale still works meanwhile.

Builds fail with "buildctl": executable file not found in $PATH

buildctl is installed in Kanea's own bin directory, and the kanead unit does not have that directory on its PATH. kanea doctor reports it under the buildkit check.

Rewrite the units and restart: run sudo kanea init, which is safe to repeat, then sudo systemctl daemon-reload && sudo systemctl restart kanead.
