A static site

Two replicas behind a Let's Encrypt certificate, with a health check.

Before you run it:

  • Point example.com and www.example.com at the node, and keep ports 80 and 443 reachable.
  • Set acme.email in the node config. Without it the node requests no certificate. Domains and HTTPS has the steps.
site.hcl
spec_version = 1

project "web" {}

service "site" {
  project = "web"
  count   = 2

  task "nginx" {
    image = "nginx:1.27-alpine"

    resources {
      cpu    = 200
      memory = 128
    }
  }

  network {
    port "http" { container = 80 }
  }

  expose {
    domains = ["example.com", "www.example.com"]
    tls { mode = "acme" }
  }

  health_check "http" {
    type     = "http"
    path     = "/"
    port     = "http"
    interval = "10s"
    timeout  = "2s"
    failures = 3
  }
}
kanea plan site.hcl
kanea run site.hcl --wait=60s
kanea status web/site

Keep the health check when you adapt this. A rolling deploy waits on it, and so does any service that lists this one in depends_on. It is also how a replica that stops answering shows up in kanea status.

To serve your own image, add a build block. The pipeline then builds and pins a digest on every push.

Two apps and a database

A frontend and an API that share PostgreSQL and Redis. depends_on holds the apps back until their backends are healthy, which is why postgres and redis declare checks.

The ${service.…} references resolve to internal DNS names when an alloc starts, so the file hard-codes no address. One secret is referenced from two services and never written in the file.

paste.hcl
spec_version = 1

project "paste" {
  description = "Pastebin: frontend, API, database, cache"
}

storage "db-data" {
  type = "local"
}

service "postgres" {
  project = "paste"

  task "db" {
    image = "postgres:16-alpine"
    env = {
      POSTGRES_DB       = "paste"
      POSTGRES_USER     = "paste"
      POSTGRES_PASSWORD = "secret:paste/db-password"
    }
    resources {
      cpu    = 1000
      memory = 1024
    }
  }

  network {
    port "pg" { container = 5432 }
  }

  volume "data" {
    storage    = "db-data"
    mount_path = "/var/lib/postgresql/data"
  }

  health_check "up" {
    type     = "tcp"
    port     = "pg"
    interval = "10s"
  }
}

service "redis" {
  project = "paste"

  task "cache" {
    image   = "redis:7-alpine"
    command = ["redis-server", "--save", ""]
    resources {
      cpu    = 250
      memory = 256
    }
  }

  network {
    port "redis" { container = 6379 }
  }

  health_check "up" {
    type     = "tcp"
    port     = "redis"
    interval = "10s"
  }
}

service "api" {
  project    = "paste"
  count      = 2
  depends_on = ["postgres", "redis"]

  task "app" {
    image = "registry.example.com/paste/api:1.4.2"
    env = {
      DB_HOST     = "${service.postgres.host}"
      DB_PORT     = "${service.postgres.port.pg}"
      DB_USER     = "paste"
      DB_PASSWORD = "secret:paste/db-password"
      REDIS_ADDR  = "${service.redis.host}:${service.redis.port.redis}"
    }
    resources {
      cpu    = 500
      memory = 512
    }
  }

  network {
    port "http" { container = 8080 }
  }

  expose {
    domains = ["api.paste.example.com"]
    tls { mode = "acme" }

    rate_limit {
      requests = 300
      window   = "1m"
      per      = "ip"
      burst    = 50
    }
  }

  health_check "http" {
    type     = "http"
    path     = "/healthz"
    port     = "http"
    interval = "10s"
    timeout  = "2s"
    failures = 3
  }

  update {
    strategy     = "rolling"
    max_parallel = 1
    min_healthy  = "30s"
  }
}

service "web" {
  project    = "paste"
  count      = 2
  depends_on = ["api"]

  task "app" {
    image = "registry.example.com/paste/web:1.4.2"
    env = {
      API_URL = "http://${service.api.host}:${service.api.port.http}"
    }
    resources {
      cpu    = 250
      memory = 256
    }
  }

  network {
    port "http" { container = 3000 }
  }

  expose {
    domains = ["paste.example.com"]
    tls { mode = "acme" }
  }

  health_check "http" {
    type     = "http"
    path     = "/"
    port     = "http"
    interval = "10s"
    timeout  = "2s"
    failures = 3
  }
}

Create the secret, then deploy. Secrets explains kanea secret put. 

kanea secret put paste/db-password     # value on stdin
kanea run paste.hcl --wait=90s

Three details worth copying:

  • redis-server --save "" is written as an argument array, which can carry the empty argument. A shell string could not.
  • The rate limit sits on the API route only. On the frontend it would limit your own pages.
  • postgres and redis declare no expose and no publish. Only this project's services reach them.

Jellyfin with local media

A media server reads a directory you already own and transcodes on a GPU. A spec cannot grant itself either one: the node has to allow the host path and define the device grant.

  1. Allow the path and define the grant on the node

    Add both to /etc/kanea/kanea.hcl:

    # /etc/kanea/kanea.hcl
storage {
  allowed_host_paths = ["/srv/media"]
}

device "gpu" {
  nodes = ["/dev/dri/renderD128"]
  allow = ["media"]
}

    /srv/media must already exist. Host paths and device grants are explained in Volumes and host access.

  2. Restart kanead

    Run sudo systemctl restart kanead. kanead reads the node config once, at startup. Running workloads are not interrupted.

  3. Deploy the spec

    Save the file below as media.hcl and run kanea run media.hcl. Jellyfin answers at http://<node>:8096 from the LAN.

media.hcl
spec_version = 1

project "media" {}

storage "config" {
  type = "local"
}

storage "library" {
  type = "host"
  path = "/srv/media"
}

service "jellyfin" {
  project = "media"

  task "app" {
    image = "jellyfin/jellyfin:10.9.11"

    device "dri" {
      grant = "gpu" # hardware transcoding; the grant is defined on the node
    }

    resources {
      cpu    = 4000
      memory = 4096
    }
  }

  network {
    port "http" { container = 8096 }

    publish "http" {
      host = 8096 # http://<node>:8096, LAN only
      ip_restriction { allow = ["192.168.0.0/16"] }
    }
  }

  volume "config" {
    storage    = "config"
    mount_path = "/config"
  }

  volume "media" {
    storage    = "library"
    mount_path = "/media"
    read_only  = true
  }

  health_check "http" {
    type     = "http"
    path     = "/health"
    port     = "http"
    interval = "15s"
    timeout  = "5s"
    failures = 3
  }
}

Without the node's half the spec is valid and the alloc fails with a message naming the missing grant. It does not start without the GPU, because a transcoder that falls back to software looks healthy and is not.

  • The library is mounted read_only. /config is an ordinary local volume that Kanea manages.
  • The publish block binds port 8096 on the node, and the edge enforces the CIDR allowlist. The port must be inside the node's edge.publish.ports range.
  • For access from outside, add an expose block with a domain. Do not widen the CIDR.

SMB and S3 volumes

The same volume block, backed by storage that is not on the node: a file browser over a NAS share and a read-only bucket.

Each driver takes its credential from one secret whose value is <user>:<secret>: username and password for SMB, access key and secret key for S3. Omit auth_ref for a public bucket or an open share.

files.hcl
spec_version = 1

project "files" {}

# A share on the NAS. The secret's value is "<username>:<password>".
storage "nas" {
  type     = "smb"
  server   = "192.168.1.20"
  share    = "documents"
  auth_ref = "secret:files/nas"
}

# A bucket, read-only. The secret's value is "<access-key>:<secret-key>".
storage "archive" {
  type     = "s3"
  bucket   = "household-archive"
  endpoint = "https://minio.internal:9000" # omit for AWS S3
  auth_ref = "secret:files/archive"
  mode     = "ro"                          # mountpoint-s3; "rw" selects s3fs
}

service "filebrowser" {
  project = "files"

  task "app" {
    image = "filebrowser/filebrowser:v2.32.0"

    user {
      uid = 1000
      gid = 1000
    }

    resources {
      cpu    = 500
      memory = 256
    }
  }

  network {
    port "http" { container = 80 }
  }

  expose {
    domains = ["files.example.com"]
    tls { mode = "acme" }
  }

  volume "documents" {
    storage    = "nas"
    mount_path = "/srv/documents"
  }

  volume "archive" {
    storage    = "archive"
    mount_path = "/srv/archive"
    read_only  = true
  }

  health_check "http" {
    type     = "http"
    path     = "/health"
    port     = "http"
    interval = "15s"
    timeout  = "5s"
    failures = 3
  }
}

Create both secrets, then deploy:

kanea secret put files/nas          # username:password on stdin
kanea secret put files/archive      # access-key:secret-key
kanea run files.hcl
  • The user block makes the process run as 1000:1000, and the volumes inherit that ownership. It travels in the mount options, so it works on a share the NAS controls.
  • host and nfs volumes cannot carry ownership. Declaring it on one is a plan error, and inheritance skips them.
  • mode on the S3 storage selects the driver: "ro" is mountpoint-s3 and the default, "rw" is s3fs. Keep a bucket for bulk, read-mostly data.
  • A custom endpoint points at MinIO or another S3-compatible store. Omit it for AWS.
  • An nfs export has the same shape, with server and export.
  • A mount that cannot be established fails the alloc. A mount that dies later is remounted.

Volumes and host access covers the network drivers, and the storage reference lists every attribute.

A Kafka cluster (KRaft)

Three brokers and no ZooKeeper. Each broker is its own service with one replica, because a broker has an identity: a node id and an advertised name that must survive restarts. Replicas of one service are interchangeable.

Three services give each broker its own DNS name, its own data volume and its own line in the quorum.

kafka.hcl
spec_version = 1

project "kafka" {
  description = "Three-broker KRaft cluster, no ZooKeeper"
}

storage "kafka-data" {
  type = "local"
}

service "kafka-1" {
  project = "kafka"

  task "broker" {
    image = "apache/kafka:4.0.0"
    env = {
      KAFKA_NODE_ID                          = "1"
      KAFKA_PROCESS_ROLES                    = "broker,controller"
      KAFKA_LISTENERS                        = "PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093"
      KAFKA_ADVERTISED_LISTENERS             = "PLAINTEXT://kafka-1.kafka.kanea:9092"
      KAFKA_CONTROLLER_LISTENER_NAMES        = "CONTROLLER"
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP   = "PLAINTEXT:PLAINTEXT,CONTROLLER:PLAINTEXT"
      KAFKA_CONTROLLER_QUORUM_VOTERS         = "1@kafka-1.kafka.kanea:9093,2@kafka-2.kafka.kanea:9093,3@kafka-3.kafka.kanea:9093"
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR = "3"
      KAFKA_LOG_DIRS                         = "/var/lib/kafka/data"
      CLUSTER_ID                             = "MkU3OEVBNTcwNTJENDM2Qg"
    }
    resources {
      cpu    = 1000
      memory = 2048
    }
  }

  network {
    port "client"     { container = 9092 }
    port "controller" { container = 9093 }
  }

  volume "data" {
    storage    = "kafka-data"
    mount_path = "/var/lib/kafka/data"
  }

  health_check "up" {
    type     = "tcp"
    port     = "client"
    interval = "15s"
    timeout  = "5s"
    failures = 3
  }
}

kanea run kafka.hcl --wait=120s
kanea ps --project=kafka
kanea logs kafka/kafka-1 --tail=50    # watch the quorum form
  • The quorum voters and advertised listeners are literal internal DNS names, <service>.<project>.kanea. A ${service.…} reference is also a start dependency, and three brokers referencing each other is a cycle that kanea plan rejects.
  • The shared storage "kafka-data" block is safe. Each service's volume gets its own directory beneath it.
  • A client in the same project bootstraps with all three names: kafka-1.kafka.kanea:9092,kafka-2.kafka.kanea:9092,kafka-3.kafka.kanea:9092.
  • A service in another project also needs allow_from naming it on each broker.
  • Do not publish port 9092. Kafka hands clients the advertised names, and those resolve only inside the node.
  • Generate your own CLUSTER_ID with kafka-storage.sh random-uuid.
