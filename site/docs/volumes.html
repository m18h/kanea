Volumes and host access

Give a service storage that outlives its containers, or access to something on the host. Each section shows what to allow on the node and what to write in the spec.

Storage takes two blocks in a spec. A top-level storage block names a backend. A service's volume block mounts one of them by name.

Storage typeWhat it mountsNode setup
localA directory Kanea creates and managesNone
hostA directory you already own on the nodeAn allowlist entry in the node config
nfs, smb, s3An export, a share or a bucketThe mount helper installed on the host

Devices and unix sockets are not storage. They use grants, which the node defines and a spec asks for by name.

Local volumes

Declare a local storage and mount it. The node needs no setup.

storage "data" {
  type = "local"
}

service "db" {
  project = "shop"
  # task, network …

  volume "pgdata" {
    storage    = "data"
    mount_path = "/var/lib/postgresql/data"
  }
}

Kanea creates the directory under the node's volume directory, at <volume_dir>/<project>/<service>/<index>/<volume>. The volume directory is /var/lib/kanea/volumes unless storage.volume_dir says otherwise.

  • Each alloc gets its own directory. Two replicas of a service never share one.
  • The alloc index is stable, so an alloc finds its data again after a restart or a replacement.
  • Removing a service keeps its volume data on disk.

A volume inherits its owner from the task's user block. The volume reference lists every field.

Host directories

A host volume mounts a directory that already exists on the node. Whether it may be mounted is the node's decision, and the allowlist is empty by default.

  1. Allow a parent directory on the node

    Add the storage stanza to /etc/kanea/kanea.hcl, the node config. Each entry permits itself and everything beneath it. The file must pass the node config's trust check. 

    # /etc/kanea/kanea.hcl
storage {
  allowed_host_paths = ["/srv/kanea", "/mnt/media"]
}

  2. Restart kanead

    Run sudo systemctl restart kanead. kanead refuses to start if an entry is not absolute, does not exist, or is "/".

  3. Declare the storage and mount it

    storage "library" {
  type = "host"
  path = "/mnt/media/library"
}

service "jellyfin" {
  project = "media"
  # task, network …

  volume "library" {
    storage    = "library"
    mount_path = "/media"
    read_only  = true
  }
}

  4. Deploy and check the mount

    kanea run media.hcl
kanea volume list

    The storage media/library appears with its path and one mount under it.

SituationResult
The path is outside every allowed parentThe alloc fails. The check runs on the path after symlinks are resolved.
The path does not existThe alloc fails, so a typo cannot become an empty volume.
The path does not exist and the storage sets create = trueKanea creates it with mode 0750, and only inside an allowed parent.
The path is a file or a socketThe alloc fails. Only directories are mounted.
The path is relative, contains .., or is /kanea plan reports an error.
The volume declares uid or gidkanea plan reports an error. Kanea never changes who owns a host directory.

The allowlist applies to every project on the node. To limit something to named projects, use a grant.

Network shares and buckets

NFS, SMB and S3 use the same two blocks. The node config needs no entry, but the host needs the matching mount helper: an NFS client, mount.cifs, mount-s3, or s3fs for a read-write bucket.

  1. Store the credential as a secret

    The value is <username>:<password> for SMB and <access-key>:<secret-key> for S3. Skip this step for an open share, a public bucket or NFS. 

    kanea secret put media/nas          # username:password on stdin
kanea secret put media/archive      # access-key:secret-key

  2. Declare the storage

    storage "films" {
  type   = "nfs"
  server = "192.168.1.20"
  export = "/volume1/films"
}

storage "photos" {
  type     = "smb"
  server   = "192.168.1.20"
  share    = "photos"
  auth_ref = "secret:media/nas"
}

storage "archive" {
  type     = "s3"
  bucket   = "media-archive"
  endpoint = "https://s3.eu-central-1.amazonaws.com"
  auth_ref = "secret:media/archive"
}

  3. Mount it in a service

    volume "films" {
  storage    = "films"
  mount_path = "/srv/films"
}

  4. Deploy and check the mount state

    Run kanea run on the spec, then kanea volume list. The state column shows whether each mount is established.

  • A network volume is mounted once per service and shared by all of its allocs.
  • A mount that cannot be established fails the alloc. The service never starts beside an empty directory.
  • A mount that stops answering is retried. Kanea emits volume.mount_failed, and volume.mount_recovered when it is back.
  • The credential is written to a 0600 file at mount time. It never appears on a command line.
  • An S3 endpoint must be https://, because the credential is sent to it on every request.
  • An S3 bucket is read-only unless the storage sets mode = "rw".

The storage reference lists the fields of each type and explains why an S3 bucket suits bulk, read-mostly data only. A complete example is in Sample stacks.

Devices and sockets

A GPU, a USB device or a unix socket reaches a container through a grant. The node config maps a grant name to paths and lists the projects that may use it. A spec names the grant and has no field for a path.

  1. Define the grant on the node

    The label is the grant's name. nodes lists the device node paths, and allow lists the projects. Both are required. 

    # /etc/kanea/kanea.hcl
device "gpu" {
  nodes = ["/dev/dri/card0", "/dev/dri/renderD128"]
  allow = ["media"]
}

  2. Restart kanead

    Run sudo systemctl restart kanead. Grants are read once, at startup.

  3. Ask for the grant in the spec

    service "jellyfin" {
  project = "media"

  task "app" {
    image = "jellyfin/jellyfin:10.9.11"

    device "dri" {
      grant = "gpu"
    }
  }
}

  4. Deploy and check the alloc

    Run kanea run on the spec, then kanea ps. The alloc reaches running, and the devices appear inside the container at their host paths.

A device grant gives read and write access. Add mode = "rwm" to the grant to also permit mknod.

SituationResult
The node has no grant of that nameThe alloc fails. The message lists the grants the node does have.
The grant does not allow the service's projectThe alloc fails.
A device path is missing, or is not a deviceThat alloc fails with a message naming the grant. kanead keeps running, because paths are checked per alloc.
A grant lists no projects in allowkanead refuses to start.

Grant a unix socket

A socket grant takes one path. The spec says where the socket appears inside the container. 

# /etc/kanea/kanea.hcl
socket "containerd" {
  path  = "/run/kanea/containerd.sock"
  allow = ["ops"]
}
task "app" {
  image = "ghcr.io/example/image-updater:1.4"

  socket "runtime" {
    grant      = "containerd"
    mount_path = "/run/containerd/containerd.sock"
  }
}
A socket grant is root on the node

A container that holds the runtime socket can start other containers without Kanea's hardening defaults. read_only restricts the filesystem entry and not the protocol spoken over it.

The control is where the grant lives: in a file on the node that no spec author can write, naming the projects it trusts.

The attribute tables are in the node config reference under device and socket, and in the spec reference under device and socket.

Check usage and budgets

kanea volume list shows every storage resource with the mounts that use it, their measured usage, their size and their mount state.

A volume block may declare size = "10GiB". That is a budget and not a quota: Kanea measures the volume against it and nothing enforces it.

  • Crossing the budget emits volume.over_budget. Dropping back under it emits volume.under_budget.
  • An s3 volume is never measured, and declaring a size on one is a plan error.
