Get started

Install a node

Two commands turn a Linux machine into a node. The install script puts one binary at /usr/local/bin/kanea. sudo kanea init does the rest: the runtime, the master key, the systemd units and your admin account.

Requirements

RequirementWhat it must be
Architectureslinux/amd64, linux/arm64. Anything else is refused before a byte is downloaded.
KernelLinux ≥ 5.10, cgroups v2 unified hierarchy. The network is eBPF, which runs only on Linux.
Init systemsystemd.
ClockNTP-synchronised. Certificates and audit timestamps depend on it.

You do not install containerd, runc, rootless buildkitd or the wasmtime shim yourself. kanea init installs them at versions pinned by SHA-256 inside the binary. The network layer needs no component, because the eBPF datapath is compiled into kanea.

To keep a containerd that is already on the machine, pass --containerd external to kanea init.

Run the install script

curl -fsSL https://m18h.github.io/kanea/install.sh | sudo bash

The script resolves the latest release, downloads the archive for this architecture, verifies it, installs one binary, and stops. It generates no keys, starts no services and writes no units. Running it on a node that is serving traffic changes nothing until you act on what it prints.

The script takes no arguments. Its settings are environment variables, and sudo does not forward them by default. Pass them as sudo VAR=value bash, or use sudo -E.

VariableDefaultMeaning
KANEA_VERSIONlatestThe release tag to install, for example vX.Y.Z. latest is resolved from a GitHub redirect, so the script needs no jq and hits no API rate limit.
KANEA_PREFIX/usr/local/binDirectory the binary is installed into, mode 0755.
KANEA_REPOm18h/kaneaThe owner/repo releases come from, so a fork installs from itself.
KANEA_REQUIRE_SIGNATURE0Set to 1 to make the cosign verification mandatory. A missing cosign binary or an unsigned release then stops the install. The script never downloads cosign for itself.
 
curl -fsSL https://m18h.github.io/kanea/install.sh | sudo KANEA_VERSION=vX.Y.Z bash

The node needs curl, tar and install, and the script must run under bash, not sh. It refuses four situations before downloading anything: a non-Linux kernel, an architecture other than amd64 or arm64, an unreachable release endpoint, and a repository with no published release.

What the script verifies

The checksum is mandatory and no setting skips it. The script downloads checksums.txt, takes the line for the archive it fetched, and runs it through sha256sum -c. A mismatch stops with checksum mismatch: do not run this binary.

The Sigstore signature over checksums.txt is checked when cosign is on PATH. The signature is keyless and bound to this repository's release workflow through the GitHub OIDC issuer.

SituationDefaultWith KANEA_REQUIRE_SIGNATURE=1
cosign present, signature validPrints Signature verified.The same.
cosign present, signature invalidFatal. The install stops.Fatal.
cosign present, no signature publishedA note, then the install continues on the checksum alone.Fatal.
cosign absentPrints cosign not found; checksum verified but signature not checked and continues.Fatal.

Installing cosign first is the stronger path. Installing by hand is the same check written out.

Note

The script has one side effect beyond the binary. It creates the kanea-edge system account if it is missing, because the edge runs as that user and not as root. A failure here is a warning and the install continues.

Set up the node

sudo kanea init runs the preflight checks, installs the host components, generates the master key, writes the node config and the systemd units, starts kanead, and creates the first admin account. Run it once, as root.

  1. Decide where the master key will be recorded

    The key is printed once during init. Without it, every backup this node makes is unreadable and every stored secret is unrecoverable. Have a password manager or a piece of paper ready before you start.

  2. Run init

    sudo kanea init

    Init prints its version and asks its first question.

  3. Choose the listen address

    Press Enter to accept 127.0.0.1:8600, type an address such as 192.168.1.10:8600 to reach the dashboard from other machines, or answer none to keep the API on its unix socket only. Init then checks the node and installs the host components, printing one line per check and per component.

    Init asks this only when --listen is not passed and stdin is a terminal. A bind.api_addr already in the node config also replaces the question.

  4. Record the master key and type it back

    Init prints the key and waits for you to retype it exactly. A mismatch writes nothing and stops. No flag accepts the key unseen. On a match, init writes the key to /var/lib/kanea/master.key, then the node config and the units, and starts kanead.

  5. Create the first admin account

    Enter a username, then a password twice. Pass --admin-user to skip the username prompt. Init answers Created admin account "<name>".

  6. Read the summary

    Init ends with Kanea is running., the dashboard URL, the internal DNS address and the three address ranges. Open the dashboard URL and sign in with the account you created.

  7. Allow your user to run the CLI without sudo

    sudo usermod -aG kanea $USER

    Log in again for the group to apply. The CLI reaches kanead over a root-owned socket, and membership of the kanea group is root-equivalent, like the docker group.

Every prompt in a run shares one reader, so a piped install answers the same questions in the same order as a typed one.

The node config init writes

Init writes /etc/kanea/kanea.hcl. With every default accepted, the file is: 

data_dir      = "/var/lib/kanea"
alloc_log_dir = "/var/log/kanea/allocs"

network {
  node_cidr    = "10.244.0.0/24"
  cluster_cidr = "10.244.0.0/16"
}

edge {
  certs_group = "kanea-edge"
}

bind {
  api_addr = "127.0.0.1:8600"
}

Init pins the directories and address ranges so the node keeps them whatever a later release chooses as a default. Answering none to the listen question leaves api_addr out. An address beyond loopback also gets api_cert and api_key.

Every other setting on the node is an attribute of this file, listed in the node config reference.

TLS for the dashboard

Beyond loopback the listener is served over TLS. Without a --listen-cert and --listen-key pair, init mints a ten-year self-signed pair at /etc/kanea/api.crt and api.key, with the key at mode 0600. It mints the pair once and never again, so the fingerprint you accepted in a browser stays the same.

Init refuses an unspecified host such as 0.0.0.0 or :8600, because the certificate needs an address or a name to carry. Bind a specific address, or set bind.api_domain. The other TLS modes, including a public certificate, are described under reaching the dashboard.

What a re-run does

Running sudo kanea init again is safe. It regenerates the units and keeps the key, the certificate, the accounts and your settings.

KeptRewritten
The master key. An existing key is never regenerated.The four systemd units, every time, at mode 0644.
The api.crt/api.key pair. Half a pair is an error.The containerd config and the component units.
The first admin. If any account exists, the step is skipped.
Every setting already in /etc/kanea/kanea.hcl, with its comments and layout. Init adds what is missing and changes an attribute only when you pass its flag.

A re-run with no flags that finds nothing missing leaves the file untouched. Init restarts kanead only when the listener it settled differs from the running one.

Host components

kanea init installs containerd, runc, rootless buildkitd and the wasmtime shim for you. Their versions and SHA-256 hashes are compiled into the binary and never fetched. kanea doctor checks the node against the same list. 

kanea install --list         # the pinned versions, straight from the binary
sudo kanea install --dry-run # resolve and verify every artefact, write nothing
sudo kanea install           # kanea init runs this for you

Nothing at a distribution's paths is touched. Kanea's containerd lives under /usr/local/lib/kanea and listens on its own socket at /run/kanea/containerd.sock, so Docker on the same machine keeps working.

FlagMeaning
--listPrint the pinned versions and exit. Needs no network and no root.
--dry-runDownload and verify everything, write nothing. Run it before an upgrade to see what would move.
--onlyComma-separated component names. They install in manifest order whatever order you give: containerd and runc first, then the buildkit image, which is pulled through the running containerd.
--forceReinstall components already at the pinned version.
--bundleInstall from an offline bundle. Network fetching is off entirely.
--containerd externalAdopt an existing containerd. Kanea installs none and writes a slice override for the existing unit.
--archTarget architecture. Meaningful only with --dry-run; installing for a foreign architecture is refused.
--prefix, --conf-dir, --data-dir, --run-dir, --unit-dirWhere binaries, configuration, state, sockets and units go.
--skip-unitsBinaries only. This also skips the image components, since containerd is never started.

Install by hand

Each release publishes one archive per architecture with an SPDX SBOM beside it, a kanea_<version>_source.spdx.json for the build's own dependency graph, a checksums.txt, and a keyless cosign signature over that file. The SBOMs are listed inside the checksums, so the one signature covers them too. 

VERSION=vX.Y.Z; ARCH=amd64   # the tag you want, e.g. from the releases page
BASE=https://github.com/m18h/kanea/releases/download/$VERSION

curl -fLO $BASE/kanea_${VERSION#v}_linux_$ARCH.tar.gz
curl -fL -O $BASE/checksums.txt -O $BASE/checksums.txt.sig -O $BASE/checksums.txt.pem

cosign verify-blob \
  --certificate checksums.txt.pem \
  --signature   checksums.txt.sig \
  --certificate-identity-regexp "https://github.com/m18h/kanea/" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  checksums.txt

sha256sum --ignore-missing -c checksums.txt
tar xzf kanea_${VERSION#v}_linux_$ARCH.tar.gz
sudo install -m 0755 kanea /usr/local/bin/kanea

There is no long-lived signing key. Sigstore binds the signature to the release workflow in this repository, and the proof is in a public transparency log. Then continue at sudo kanea init.

Homebrew

brew tap m18h/kanea
brew trust m18h/kanea   # brew ≥ 6 refuses formulae from untrusted third-party taps
brew install kanea

Homebrew installs the kanea CLI, and a Mac is a full client. With KANEA_URL and a token it drives a remote node: plan, run, ps, logs, exec, scale. A Mac is never the node, because both daemons need Linux.

On Linux the formula installs the same binary, but install a node with the script above. That puts the binary at /usr/local/bin, owned by root, where kanea upgrade can replace it. If brew owns the binary on a node, upgrade with brew upgrade kanea, then sudo kanea upgrade --no-fetch to restart onto it.

The formula lives in its own tap, m18h/homebrew-kanea, and is regenerated from each release's checksums.txt.

The container image

docker run --rm ghcr.io/m18h/kanea:latest version

# the shape a pipeline uses: the spec on a mount, the node over the network
docker run --rm -v "$PWD:/workspace:ro" \
  -e KANEA_URL -e KANEA_TOKEN \
  ghcr.io/m18h/kanea:vX.Y.Z run shop.hcl   # pin the tag in a pipeline

Use the image in a pipeline that deploys to a node. It carries the CLI and is not a way to run a node: agent, edge, init, install, doctor and upgrade act on a host and its systemd, which a container does not have.

One manifest list covers linux/amd64 and linux/arm64, tagged vX.Y.Z and latest. latest moves only for a plain vX.Y.Z release, never for a prerelease.

The image contains the released binary, not a rebuild of it. The release workflow builds the image from the same archives you can download, after verifying checksums.txt under its signature and each archive against it. The hashes you can verify by hand therefore describe what is inside the image.

The image digest is signed with the same keyless identity as the checksums and carries an SPDX attestation: 

cosign verify ghcr.io/m18h/kanea:vX.Y.Z \
  --certificate-identity-regexp 'https://github.com/m18h/kanea/' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com'

The container runs as an unprivileged user (uid 65532) with /workspace as its working directory, so mount your spec there.

If your network terminates TLS with its own CA, add the root to /usr/local/share/ca-certificates and run update-ca-certificates in a derived image. Or pass the node's CA with KANEA_CA_CERT, which replaces the system pool: the CLI then trusts that CA and no public one.

Air-gapped nodes

A node with no egress installs from a bundle. Build the bundle on a machine with a network, carry it across, and pass it to init: 

kanea bundle create --arch amd64 -o kanea-bundle.tar.gz   # connected machine
sudo kanea init --bundle kanea-bundle.tar.gz              # air-gapped node

The bundle carries no hashes of its own. Its contents are verified against the hashes compiled into the installing node's binary, so a tampered bundle cannot vouch for itself. Each release publishes one bundle per architecture, covered by the same signed checksums.txt.

The bundle covers Kanea's own components. Your workload images still come from a registry the node can reach, unless they are preloaded. On a node with preloaded images, set pull_policy = "never" in the images stanza so an absent image fails at once, by name.

kanea doctor --offline skips the single network probe. On a node with no route to the release endpoint, kanea upgrade stops with a pointer to this flow.
