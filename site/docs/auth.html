Sign-in and access

Decide who may use the node. Create accounts for people and tokens for scripts, or let people sign in through an identity provider or a directory.

CallerAuthenticates withRole comes from
A person at the dashboardA local account, OIDC or LDAPThe account, a token claim, or a directory group
A script, CI job or remote CLIAn API tokenThe token
The CLI on the node itselfThe local unix socketAlways admin

There are two roles. An admin may change anything. A viewer may read and nothing else.

Local accounts

Accounts live in the Store, so they take effect at once and need no restart. kanea init creates the first admin.

  1. Add an account

    kanea user add --role=viewer dana

    The command prompts for a password of at least 12 characters and prints wrote account dana (viewer). Without --role the account is an admin. In a script, pipe the password in on standard input.

  2. List accounts

    kanea user ls

    The table shows each name, its role, and when it was created and updated.

  3. Remove an account

    kanea user rm dana

    The account's sessions end with it. Kanea refuses to remove or demote the only admin account.

  • Running kanea user add for an existing name replaces its password and role, and ends its sessions.
  • kanea user revoke-sessions <name> ends every session a name holds and keeps the account. It works for OIDC and LDAP names too.
  • A session lasts 12 hours.
  • People who sign in through OIDC or LDAP never appear in kanea user ls. They hold a session and have no account.

The Accounts tab of the dashboard's Settings page manages the same accounts, and API tokens with them.

API tokens

A token lets a script, a CI job or a remote CLI call the API. It carries a name and a role. There are no finer scopes.

  1. Create a token

    kanea token create --role=admin --expires-in=720h ci > ci.token

    The token is written to standard output once and cannot be shown again. The default role is viewer. Without --expires-in the token never expires, and the command warns you.

  2. Use it

    Set KANEA_TOKEN beside KANEA_URL, or pass --token. Remote nodes and CI has the full setup.

  3. List and revoke

    kanea token ls
kanea token rm <id>

    The list shows each token's id, name, role, age and expiry. Revoke by id, not by name.

Single sign-on with OIDC

Add an auth { oidc { … } } block and the dashboard's sign-in page gains a Continue with SSO button. Password login keeps working beside it.

  1. Register Kanea with your provider

    Create a client and register one redirect URI: the dashboard's address followed by /v1/auth/oidc/callback. Note the client id and, for a confidential client, the secret.

  2. Store the client secret

    kanea secret put shared/oidc < client-secret.txt

    Skip this for a public client. Kanea uses PKCE on every login, so a client with no secret is a supported setup.

  3. Add the block to the node config

    Edit /etc/kanea/kanea.hcl, the node config. redirect_url must match the registered URI exactly. 

    # /etc/kanea/kanea.hcl
auth {
  oidc {
    issuer        = "https://auth.example.com/realms/home"
    client_id     = "kanea"
    client_secret = "secret:shared/oidc"
    redirect_url  = "https://kanea.example.com:8600/v1/auth/oidc/callback"
    admin_claims  = ["platform-admins"]
    viewer_claims = ["developers"]
  }
}

  4. Restart kanead

    Run sudo systemctl restart kanead. kanead fetches the issuer's discovery document at startup and refuses to start if it cannot.

  5. Check it worked

    Open the dashboard's sign-in page. The Continue with SSO button shows the issuer's host name. Sign in with an account that holds one of the listed claim values.

How a login gets a role

Kanea reads one claim from the ID token, groups unless role_claim names another. The claim may be a list, a single string, or a space-separated string.

  • A value listed in admin_claims gives the admin role. Admin is checked first.
  • A value listed in viewer_claims gives the viewer role.
  • No match means the login is refused. Being authenticated by the provider is not enough.

At least one of the two lists must be set, or kanead refuses to start. The name shown in the audit log is the token's preferred_username, then email, then name.

Settings worth knowing

AttributeBehaviour
issuerTurns OIDC on. Without it the other attributes do nothing and kanead logs a warning.
client_id, redirect_urlBoth required once issuer is set.
client_secretA secret: reference. A literal value is refused. Omit it for a public client.
scopesRequested in addition to openid. The default is ["profile", "email"]. An empty list requests openid alone.
role_claimThe claim that carries roles. Add the scope that makes your provider include it.

The provider must return a signed ID token. Kanea checks its signature, issuer, audience, expiry and nonce, and a login must finish within ten minutes of starting. Types and defaults are in the auth reference.

Directory sign-in with LDAP

Add an auth { ldap { … } } block and people sign in with their directory name and password, on the same form as local accounts.

  1. Store the service account's password

    kanea secret put shared/ldap-bind < bind-password.txt

    Kanea searches the directory as this account. Leave out both bind_dn and bind_password for an anonymous search.

  2. Add the block to the node config

    # /etc/kanea/kanea.hcl
auth {
  ldap {
    url           = "ldaps://dc1.corp.example.com"
    bind_dn       = "cn=kanea,ou=svc,dc=corp,dc=example,dc=com"
    bind_password = "secret:shared/ldap-bind"
    user_base_dn  = "ou=people,dc=corp,dc=example,dc=com"
    user_filter   = "(sAMAccountName=%s)"
    admin_groups  = ["cn=platform-admins,ou=groups,dc=corp,dc=example,dc=com"]
    viewer_groups = ["cn=developers,ou=groups,dc=corp,dc=example,dc=com"]
  }
}

  3. Restart kanead

    Run sudo systemctl restart kanead. A configuration error stops kanead from starting. An unreachable directory does not: kanead logs a warning and LDAP logins fail until the directory is back.

  4. Check it worked

    sudo journalctl -u kanead | grep "directory"

    The log has directory authentication configured. Sign in at the dashboard with a directory account. Each success adds a directory login verified line with the role it mapped to.

The connection

AttributeBehaviour
urlldaps://host[:port], or ldap://host[:port] with StartTLS forced. There is no cleartext option.
ca_fileA PEM file with the CA to trust, for a directory behind a private CA.
bind_dn, bind_passwordSet both or neither. The password is a secret: reference.

Finding the user

Kanea searches under user_base_dn with user_filter. The filter needs exactly one %s, which receives the typed name with special characters escaped. The default is (uid=%s).

The filter must match exactly one entry. Kanea then binds as that entry with the typed password, and the directory's answer decides the login.

Mapping groups to roles

There are two ways to learn a user's groups:

MethodConfigureGroups are
memberOfNothing. This is the default.The values of the user entry's memberOf attribute
Group searchgroup_base_dn and group_filter, bothThe DNs of the entries the filter matches

group_filter needs one %s, which receives the user's DN, as in (member=%s). The search runs as the service account.

  • admin_groups and viewer_groups hold group DNs. They are compared without regard to case.
  • Admin is checked first, so someone in both lists is an admin.
  • A user in neither list is refused. At least one list must be set, or kanead refuses to start.

Local accounts come first

Kanea consults the directory only for a name that has no local account. A directory entry can never shadow a local admin. The login rate limit applies before any bind, so the node cannot serve as a tool for guessing directory passwords.
