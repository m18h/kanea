Guides

Upgrade and uninstall

Move a node to a new release with one command, convert a node that was configured with daemon flags, or remove Kanea from a machine.

Upgrade a node

  1. See what is available

    sudo kanea upgrade --check

    The command reports three versions and changes nothing:

    Running version: vX.Y.Z
Binary version:  vX.Y.Z
Latest release:  vX.Y.Z

Run `sudo kanea upgrade` to move to it.

  2. Upgrade

    sudo kanea upgrade

    The command downloads and verifies the release, installs it, takes a backup and restarts both daemons. It ends when kanead answers on the new version: 

    Fetching vX.Y.Z (installed binary is vX.Y.Z)…
Running version: vX.Y.Z
Binary version:  vX.Y.Z

Taking a pre-upgrade backup…
  archive <id> at index <n>

Restarting the edge proxy (kanea-edge)…
Restarting the control plane (kanead)…

Waiting for the control plane…
kanead is up at vX.Y.Z

  3. Check the host components

    sudo kanea install --dry-run
sudo kanea doctor

    Each release pins its own component versions. The dry run shows whether any component needs to move, and sudo kanea install moves it. kanea doctor prints one ok line per check when the node matches the release.

Running allocs are not touched at any point. Running the command twice is safe: when the binary is already at the target version, nothing is downloaded.

What the command does

  1. Resolves the latest release, or the one named by --version.
  2. Downloads it and checks its sha256 against the release's checksums.txt.
  3. Checks the cosign signature over that file when cosign is installed. A signature that fails is fatal.
  4. Installs the binary atomically over its own path.
  5. Takes a pre-upgrade backup, if a backup destination is set.
  6. Restarts kanea-edge, then kanead.
  7. Waits for kanead, which runs any state migration at startup, to answer its health check.

The edge restarts first because it drains and returns in seconds. kanead restarts last so the state migration runs once everything else has settled. If a migration runs, kanead keeps a copy of the earlier state in the data directory; delete it once you are satisfied with the upgrade.

The command does not regenerate the systemd units. When release notes say the units changed, re-run sudo kanea init and then sudo systemctl daemon-reload. A re-run of init keeps the master key, the accounts and your settings.

Flags

FlagMeaning
--checkReport the running, installed and latest versions, and stop.
--version vX.Y.ZGo to a specific release instead of the latest.
--no-fetchDownload nothing and restart onto the binary already installed. Use it after a package manager has replaced the binary.
--require-signatureRefuse the release unless its cosign signature verifies. A missing cosign binary or an unsigned release is then fatal. The command never downloads cosign itself.
--allow-downgradePermit a target older than the running kanead. Refused by default, because the Store's schema only moves forward.
--skip-backupSkip the pre-upgrade backup. A state migration still takes its own local copy.
--timeoutHow long to wait for each service. Default 2m.
--dry-runPrint what would run and stop.

To require a signature on every upgrade, set require_signature = true in the upgrade stanza. The same stanza's repo names the repository releases come from.

Replace the binary first

Re-running the install script replaces the binary and nothing else. The daemons keep running the old one until you run sudo kanea upgrade:

re-running the install script
$ curl -fsSL https://m18h.github.io/kanea/install.sh | sudo bash
Upgrading kanea <installed> -> <latest> (linux/amd64)
Verifying the checksum
cosign not found; checksum verified but signature not checked
Installed /usr/local/bin/kanea

The running daemons are still on the old binary. Next:

    sudo kanea upgrade

It backs up, drains and restarts kanea-edge, then restarts kanead, which
runs any state migrations. Running workloads are untouched throughout.

Upgrade from the dashboard

An admin can run the same upgrade from the dashboard's Updates page. kanead takes the backup, fetches and verifies the release, installs it, restarts kanea-edge, and exits so systemd starts it on the new binary. The page reloads when the new version answers.

The node checks for a newer release only while an admin has the dashboard open, and caches the answer for an hour. The dashboard cannot downgrade; --allow-downgrade exists only on the node's CLI. Outside systemd nothing restarts: the binary is installed and the response says restart_required.

Nodes without egress

A node that cannot reach the release endpoint gets its binary and components from the offline bundle. Install the new binary, then run sudo kanea upgrade --no-fetch.

Migrating from flags

Older releases configured the daemons with flags on the ExecStart line of their systemd units, with three optional side files and two environment variables. Both daemons now take no arguments and read one file, /etc/kanea/kanea.hcl. A node installed under the old scheme converts itself the first time it starts on a new binary.

What happens automatically

Run sudo kanea upgrade as usual. You do not need to do anything else. After the binary is replaced:

  1. The edge restarts, finds flags on its command line, and exits. systemd restarts it; this happens once or twice.
  2. kanead starts, finds flags on its command line, and converts them into /etc/kanea/kanea.hcl. A flag beats a value already in the file, which is the precedence the node was running under.
  3. If the file already existed, kanead first copies it to /etc/kanea/kanea.hcl.pre-migrate.
  4. kanead rewrites both unit files so the lines read ExecStart=/usr/local/bin/kanea agent and ExecStart=/usr/local/bin/kanea edge. Nothing else in the units changes.
  5. Any drop-in under kanead.service.d/ or kanea-edge.service.d/ that sets ExecStart= is renamed to <name>.migrated.
  6. kanead reloads systemd, restarts the edge, and exits. systemd starts it again under the rewritten unit.

Both daemons are back within about ten seconds, well inside the two minutes kanea upgrade waits. Workloads are not restarted.

Note

A renamed drop-in stops applying as a whole. If it carried other directives, such as an Environment= line of your own, move them into a new drop-in that does not set ExecStart=.

Preview it or run it by hand

To see the result before upgrading, run the conversion as a dry run on the new binary: 

sudo kanea config migrate --dry-run

It prints the kanea.hcl it would write and the two new ExecStart lines, and writes nothing. To do the conversion yourself: 

sudo kanea config migrate

This writes the file, rewrites the units, reloads systemd, and restarts kanea-edge and kanead. --unit-dir names a unit directory other than /etc/systemd/system. On a node with no flags left to convert, the command reports nothing to migrate and writes nothing.

The conversion stops without writing anything in three cases: a flag it does not recognise, a result that is not a valid node config, and a kanead and edge unit that name different route or certificate files. The error names the flag or the two values. Fix the unit and run it again.

Starting a daemon with arguments by hand is refused, with a message that points at sudo kanea config migrate.

Side files

The files named by --passthrough-config, --secrets-providers-config and --tls-certs-config are folded into kanea.hcl: their device, socket, provider and certificate blocks are copied in as written. The side files stay on disk, but nothing reads them. Delete them once you have checked the new file.

A change to one of these blocks now needs a restart of kanead. The certificate pairs and credential files the blocks point at are still picked up when their content changes.

Changing a setting afterwards

Edit /etc/kanea/kanea.hcl and restart the daemon, as described under applying a change. Do not add flags back to a unit: a daemon started with arguments refuses to run.

Uninstall

These steps remove Kanea and everything it stored. The paths are the defaults; if your node config sets data_dir or alloc_log_dir, use those paths instead.

Note

The data directory, /var/lib/kanea, holds the master key, every stored secret and every local volume. Deleting it is permanent. If you may want any of it again, take a backup and copy the volume data off the node first.

  1. Stop and disable the units

    sudo systemctl disable --now kanead kanea-edge kanea-buildkit kanea-containerd

    systemctl is-active kanead kanea-edge then prints inactive twice. On a node set up with --containerd external there is no kanea-containerd unit; leave it out.

  2. Remove the unit files

    cd /etc/systemd/system
sudo rm -f kanead.service kanea-edge.service kanea-buildkit.service \
  kanea-containerd.service kanea.slice kanea-workloads.slice
sudo rm -rf kanead.service.d kanea-edge.service.d
sudo systemctl daemon-reload

    With an adopted containerd, also remove /etc/systemd/system/containerd.service.d/10-kanea-slice.conf.

  3. Reboot

    sudo reboot

    Stopping the daemons leaves workload containers running by design. A reboot ends them and clears the runtime state under /run/kanea, /run/kanea-edge and /sys/fs/bpf/kanea. With the units gone, nothing of Kanea starts again.

  4. Remove the component prefix

    sudo rm -rf /usr/local/lib/kanea

    This removes containerd, runc, buildkit and the wasmtime shim that Kanea installed.

  5. Remove the configuration

    sudo rm -rf /etc/kanea

    This removes kanea.hcl, the containerd config and the api.crt/api.key pair.

  6. Remove the data directory

    sudo rm -rf /var/lib/kanea

    This is the step that cannot be undone: the master key, the Store, the secrets, the volumes, the image store and the build cache all live here.

  7. Remove the log directory

    sudo rm -rf /var/log/kanea

  8. Remove the service accounts

    sudo userdel kanea-edge
sudo userdel kanea-buildkit
sudo userdel kanea-s3
sudo groupdel kanea

    kanea-edge runs the edge, kanea-buildkit runs builds, kanea-s3 runs the S3 mount helpers, and the kanea group grants CLI access. A command that reports an unknown user or group means that account was never created; carry on.

  9. Remove the binary

    sudo rm -f /usr/local/bin/kanea

    command -v kanea then prints nothing.

Two edits to shared system files remain, and both are harmless to leave. The installer adds user_allow_other to /etc/fuse.conf if it is not already set, and a kanea-buildkit line to /etc/subuid and /etc/subgid. Remove them by hand if you want the machine exactly as it was.
