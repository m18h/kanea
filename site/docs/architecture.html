Internals

Architecture

This page explains how Kanea is put together and why. You do not need it to run a node. Read it when you want to know what a component does under load, during a restart, or under attack.

One binary produces two long-running processes and a CLI. The datapath that networks your services is a set of eBPF programs compiled into the binary and loaded into the kernel. containerd and buildkitd are separate software that Kanea drives. kanea init installs each at a version pinned by SHA-256 in the binary, under Kanea's own prefix and sockets, so nothing already on the node changes.

Two processes, one binary

kanead is the control plane: API, dashboard, reconciler, autoscaler, GitOps, notifications and backups. The edge is the ingress proxy. It is a separate systemd unit running as a separate unprivileged user.

The split buys two things:

  • Restarting, upgrading or crashing the control plane does not interrupt public traffic. The edge unit deliberately has no After=kanead.service.
  • The process that terminates untrusted public traffic cannot change the platform. It has no Store access and no write path.

How the edge learns its routes

bbolt locks the whole database file, so a second process opening it would block until kanead exits, even read-only. The edge therefore never opens it. kanead projects what the edge needs into two files under /run/kanea-edge/:

FileModeHolds
routes.json0644Host to service frontend. Nothing secret: the domains are in public DNS.
certs.json0640Certificates and their private keys.

Two files with two permission sets mean neither compromises for the other. The paths are the defaults of edge.routes_file and edge.certs_file in the node config.

kanead writes each file to a temporary name and renames it, so a half-written file is never visible. The projection carries the Store index it was built from, which lets the edge recognise a stale snapshot.

A missing or stale snapshot is not an outage. The edge keeps serving the last table it loaded for as long as kanead is away, and it starts with an empty table if it has none. A control plane that is down must never take the site down with it.

The Store

One embedded bbolt database holds every mutation, behind a Store interface with monotonic indexes. Its buckets are projects, services, allocs, events, certs, secrets, pipelines, audit and kv.

  • Single writer. All mutations serialise. Reads are bounded and paginated, because a long read transaction blocks the writer.
  • Raft-shaped on purpose. The interface and its index semantics are what a Raft state machine needs, so a clustered implementation can replace it without touching call sites.
  • Metrics and logs never touch it. Time series live in a bounded in-memory ring, and logs go to files through non-blocking drains. A metrics write that contended with the reconciler's writer would make observability and convergence fail together.
  • Migrations are explicit. The Store does not migrate itself when opened. A migration rewrites state in place, so kanead copies the database first, in the one window where it is open and the migration has not started.

Runtime driver: containerd

kanead drives containerd over its socket with the official Go client. Each project gets its own containerd namespace, kanea-<project>, so images and containers are isolated between projects by construction.

The driver pulls images, runs the task lifecycle, sets up each alloc's network namespace, samples cgroup metrics and captures stdout and stderr. Pull credentials come from the secrets store, and a spec can pin an image by digest.

Hardening is not opt-in

Every alloc starts with:

  • a baseline capability set: the uid-switching capabilities an image needs to chown a volume and drop to its configured user, and nothing more;
  • no-new-privileges;
  • the default seccomp profile;
  • its own PID and IPC namespaces.

CAP_NET_RAW is excluded from the baseline. Binding port 80 needs no capability, because the alloc's network namespace has no privileged-port floor.

capabilities = ["none"] drops everything. A workload that needs a capability beyond the baseline names it in the spec, and Kanea accepts it only from a permitted set. Capabilities equivalent to full privilege are rejected when the spec is parsed.

No spec can lift any of this on its own: there is no privileged field. The one way past these defaults is a grant, a host device or socket the operator defines on the node. A spec requests a grant by name and can never define one.

The restricted posture

hardening = "restricted" on a service requires a non-zero user, runs the task with no capabilities and refuses any grant declared beside it. A service that owns a volume chowns it in a root init step first. task.read_only_rootfs = true mounts the image read-only on top of that.

Neither is the default, because the baseline exists so that stock images start. kanea plan warns on the weak shapes they replace: an effective uid of 0, a writable root filesystem, and an image that follows a moving tag without opting into auto-update.

Disk hygiene

One disk holds images, logs, state and volumes, so the driver keeps it in check. It garbage-collects images, caps each service's logs, and caps the build cache across both content stores: containerd's and the rootless buildkitd user's. Image GC is tunable in the node config.

Network driver: eBPF datapath

The datapath is Kanea's own: three small eBPF programs, a handful of pinned maps and plain netlink plumbing. kanead loads and writes all of it from one object compiled into the binary. There is no network agent, no key-value store and no CNI.

The loader is the standalone github.com/cilium/ebpf library. Importing github.com/cilium/cilium would pull in the Kubernetes client graph, which Kanea does not depend on.

The programs are compiled ahead of time and committed, so go build needs no clang. They read only UAPI context types, so the node needs no BTF, and there is no CO-RE and no vmlinux.h.

IP is identity

kanead allocates every alloc address from the node CIDR and every service VIP from the service CIDR, durably in the Store. The allocator that hands out an address also writes the kernel's identity map, alloc IP → {project, service}. There is no identity-allocation protocol, no label race and no settle window.

The numeric project and service ids behind the maps are allocated by the Store, monotonic and never reused. That keeps a pinned map meaningful across a kanead restart. The CIDRs are set in the network stanza.

Attach is deny-closed by construction

Per alloc, in order:

  1. create the network namespace;
  2. write the identity map;
  3. create the veth with the host side down;
  4. attach the policy programs at tc;
  5. add addresses and static neighbours;
  6. bring the link up;
  7. add the host /32 route last.

At the first moment a packet can reach or leave the alloc, policy is already enforcing and identity is already resolved. A skipped step fails closed, because an identity miss is a drop. The deny-by-default guarantee is structural, not temporal: there is no unlabelled window to hold shut with retries. Attach has no wait loop and completes in milliseconds.

Load balancing is connect-time

One cgroup connect4 program at the root cgroup, held by a pinned bpf_link, rewrites VIP:port → backend at connect(2). It applies to host processes and containers alike, which the edge depends on: it dials a VIP with a plain dialer.

There is no per-packet NAT and no conntrack entry per flow. An established connection never consults a map, so kanead can restart, or recreate every map, without touching live traffic.

Backends update by generation flip. kanead writes the new set under the next generation and commits it with one atomic map update. A concurrent connect() sees a complete old set or a complete new one, never a torn one.

A VIP with no backends refuses at connect(), so a caller gets an error at once and not a timeout. Service ports are TCP only, and kanea plan refuses anything else.

Policy is SYN-gated map entries

The tc program on each alloc's host-side veth admits three kinds of source and drops every other cluster-internal one:

  • a source carrying the host identity: the edge's upstream dials, and kanead's DNS replies and probes;
  • a source in the same project;
  • a source named by an allow_from edge in the spec.

A source outside the cluster CIDR carries no identity. It is the internet answering a connection the alloc opened, translated back by conntrack on the way in, and it passes. Nothing unsolicited arrives that way: the pod CIDR is unroutable from off the node, and published ports terminate at the edge.

The mirror rule guards the other direction. A packet leaving an alloc must carry a cluster source, so a forged external address cannot use that pass.

There is no policy file, no selector language and no translation step that could make a rule silently match nothing. Policy is map entries the datapath enforces directly. Rules only ever union, so allow_from can never weaken the project's default deny.

One deliberate weakening

Enforcement is per connection attempt. TCP that is not a SYN passes, which lets cross-project replies flow without a conntrack. That is weaker than stateful tracking: an in-node ACK probe crosses the filter and is stopped only by the receiving stack's RST. The threat model states it. Moving to an LRU conntrack map would be an additive change.

Egress and the host firewall

A second, small egress program drops the cloud-metadata range 169.254.0.0/16 in the kernel, with a drop counter per alloc. It also drops any service-CIDR destination that escaped the connect-time rewrite, and it counts traffic per endpoint.

Masquerade for routed pod traffic is one nftables rule in a table Kanea owns, named kanea. kanead re-asserts the rule and net.ipv4.ip_forward every thirty seconds, so a firewall reload that flushes the ruleset costs seconds and needs no daemon restart.

A drop policy that another tool installs can still eat alloc traffic, on the forward hook or the input hook. kanea doctor detects and names both, and passes once the ruleset accepts the cluster CIDR. kanea firewall prints the rules to add. A missing kanea table and forwarding turned off are separate findings.

Internal DNS

Allocs resolve through kanead's own resolver, on UDP and TCP. It binds to the datapath's host anchor, the node CIDR's .1 address, and never to a wildcard. It answers <service>.<project>.kanea names authoritatively and forwards everything else upstream.

By default the upstreams are the host's own /etc/resolv.conf, read once at startup and taken exactly as listed. That includes systemd-resolved's 127.0.0.53 stub, the only nameserver a stock Debian or Ubuntu server has. kanead forwards from the host's namespace, so the stub is reachable, and a workload inherits the node's cache and DNSSEC posture.

An alloc is never handed the upstream addresses: its resolv.conf names Kanea's resolver. To pin the upstreams or move the listener, set the dns stanza.

A host firewall is what usually breaks this

An alloc's query to the resolver is a new inbound connection to the host on a veth. It crosses the input hook like any other arrival, and a default-deny ufw or firewalld drops it.

It does not look like a firewall problem. The host's own dig @10.244.0.1 keeps answering, because every firewall manager accepts lo unconditionally, and the resolver's logs show a healthy server. kanea doctor names the cause and kanea firewall prints the rules.

TCP is served beside UDP because three things set the truncation bit, and each tells a client to retry over TCP: an internal answer over 512 bytes, an upstream reply that filled the read buffer, and an upstream reply that already carried TC.

The TCP half is bounded the way the UDP half is. It has a hard cap on concurrent connections whose refusals are counted, and deadlines on every connection. A TCP query is forwarded over TCP, so the retry can carry what the datagram could not.

Datapath state is derived

Programs, maps and the cgroup link are pinned under /sys/fs/bpf/kanea with a schema stamp. A kanead restart leaves the dataplane untouched. A stamp mismatch recreates and repopulates the maps inside the first reconcile pass, which is safe because established flows bypass them. Nothing under the pin root is backed up.

The edge

The edge is a Go reverse proxy. It routes by host to service frontends, terminates TLS, supports WebSocket and gRPC, redirects HTTP to HTTPS and adds security headers. Domains and HTTPS covers where its certificates come from.

The middleware chain runs in a fixed order, per service, from the spec's expose block:

Host match → IP allow/deny → rate limit → header transforms → upstream proxy

kanea plan validates all of it, and it fails closed. An ingress control that silently does nothing at runtime is worse than one that is absent.

Hardening is mandatory. The edge sets read, header and idle timeouts and header size caps against slowloris, applies upstream timeouts per route, and bounds its connection pools. It strips client-supplied X-Forwarded-* headers. It answers an unknown Host with 404, which is also the DNS-rebinding defence for the API on the same machine.

Because it already sits in the request path, the edge is the primary source of L7 metrics for exposed services: requests per second and latency percentiles at no extra data-plane cost. The datapath's map counters cover traffic between services.

ACME runs in kanead, never in the edge. Obtaining a certificate means writing one, and the edge does not write.

Resource isolation

The control plane must survive anything a workload does. Enforcement is cgroups v2, arranged as two sibling slices: 

/sys/fs/cgroup
├── kanea.slice                # kanead, kanea-edge (+ containerd and buildkitd, via their own units)
│     memory.min      = system_reserve_memory     # kernel-protected floor (default 256 MiB; build nodes raise it)
│     memory.swap.max = 0                         # the floor is RAM, not swap
│     cpu.weight      = 10000
│     OOMScoreAdjust  = -900                      # the global OOM killer picks workloads first
└── kanea-workloads.slice      # every alloc lives under this one parent
      memory.max      = total RAM − system_reserve_memory
      memory.swap.max = 0
      cpu.weight      = 100
      └── per-alloc: memory.max · cpu.max · pids.max from the spec's resources block

The reserve is the --reserve flag of kanea init, which writes it into kanea.slice.

"Memory lock" means guarantee, not mlock

Kanea does not call mlockall. The Go GC grows the heap unpredictably, and RLIMIT_MEMLOCK turns pin overflow into hard allocation failure, so the lock itself could crash kanead.

The guarantee comes from memory.min, the OOM score and no swap in the slice. Under pressure the kernel refuses to reclaim the floor.

Per-alloc limits are enforced where declared. Omit resources, or a field of it, and the alloc is unbounded in that dimension. It is then capped only by the workload slice's collective ceiling. That ceiling and the control-plane floor are what protect the platform.

pids.max is the exception: the cap is always on. Omitting it means 256, and resources { pids = 2048 } declares a different value.

Declared resources are also the admission units. kanea plan renders the workload budget, and apply refuses a total above it unless the operator has enabled oversubscription.

Metrics and autoscaling

Three scrapers feed one bounded in-memory time series:

  • containerd cgroup metrics: CPU and memory;
  • the edge: requests per second and latency percentiles for exposed services;
  • the datapath's per-CPU map counters: flows and drops between services.

The intervals and scrape addresses are in the metrics stanza.

"No data" is never zero

A missing metric and an idle service lead to opposite decisions. The time series, the evaluator, the Prometheus exporter and the dashboard each keep the two apart, and each has a test asserting it.

The evaluator applies the scaling block with guardrails and a circuit breaker. The budget is 20 seconds from a sustained breach to a decision: a 15-second averaging window, which is three samples at the 5-second scrape resolution, plus one evaluation tick. A large spike decides sooner.

The autoscaler is not a second scheduler. It writes one number, the desired count, and the reconciler converges. kanea scale uses the same route, so manual and automatic scaling cannot disagree about mechanism.

State replication and restore

kanead replicates the Store to any S3-compatible bucket. This section explains the design. To set it up, follow Back up a node.

  • Change data capture. Store mutations produce change segments. kanead ships snapshots and segments to the bucket. The S3 client is hand-written against the REST API, with SigV4 and four verbs, and CI runs it against MinIO in path-style and virtual-hosted addressing.
  • Archives are chunked AEAD. Keys are derived from the master key with HKDF. The last chunk is sealed under different additional data, so a truncated snapshot fails to decrypt and cannot restore as half a platform.
  • Manifests are unencrypted and hashes cover the ciphertext. Someone holding the bucket and no key can still see what is there and whether it is intact. That is the question to ask before fetching the escrowed key.
  • Restore is staged, never performed in place. The API can stage one, and kanead performs it at the next start, before anything opens the Store. The API has no method that restores a running node.
  • The replication cursor is derived from the sink, never stored. Writing it to the Store would emit a change that needs shipping, which would write it again.
  • The destination can change at runtime, from the dashboard's Settings page or PUT /v1/settings/backup. kanead probes a new destination with a real test write before it commits, so a typo is refused and the old replication continues. On a change, the old destination receives one final segment and the new one an immediate full snapshot. Which destination wins explains how this setting relates to the node config.

kanea init generates the master key, shows it once and asks you to type it back. Without it, every archive is unreadable. Read the DR runbook before you need it.

API, dashboard and MCP

The API is REST plus one multiplexed WebSocket, and every route is deny-by-default, including the WebSocket and every MCP route. The exceptions are /login, the ACME challenge path and /healthz.

/healthz keeps its unauthenticated answer short: the status and the OIDC issuer, which a login screen needs before it holds a credential. Version, PID, Store index, listen address and uptime need an identified caller. A bad token still gets the short 200, so a load balancer that forwards a stale Authorization header cannot flap a health check.

One route authenticates differently: the git webhook. It checks a per-project HMAC over the raw body, rejects replays and is audited. It never deploys from the request. It marks the project, and the sync loop re-reads the source with Kanea's own credential.

The dashboard is a React single-page app embedded in the binary with go:embed and served by kanead on the API listener. The dashboard covers how to reach it, and the listener is set in the bind stanza.

The MCP server exposes its tools in three tiers (read, mutate, destructive) over stdio and streamable HTTP. AI agents (MCP) lists them.

Why MCP tools have no privileges of their own

Every tool reaches the platform by making an HTTP request against the API's own handler. A tool's only verb is "send this request", so it can never be more privileged than the credential its caller presented. Nothing in the MCP package may hold a Store, a secrets store or an auth store.

There are also no secret tools at any tier. The requirement is that no tool returns a secret value. The implementation gives an agent no secrets verb at all, and a test fails if one appears.
