Secrets

Store a credential on the node and reference it from a spec. If the value lives in an external secret manager, have the node keep its copy in step.

How secrets work

A secret is never written in a spec. The spec holds a reference, secret:<project>/<name>, and Kanea resolves it when an alloc starts. Values are kept encrypted in the Store, under the node's master key.

RuleWhat it means
Write-onlyThere is no get: not in the CLI, the API or the MCP server. A value goes in and is only resolved into a running alloc.
Project-scopedA service in shop may reference secret:shop/… or secret:shared/…. Any other project's path fails validation, so kanea plan reports it.
A file by defaultThe secret is delivered as a file on a per-alloc tmpfs. An environment variable holding the value is the opt-in, weaker form.
Rotation needs a replacementA changed value reaches a service when its allocs are next replaced, for example by kanea restart shop/web.
Resolved or failedA reference to a secret that does not exist fails the alloc. The service does not start without it.

Store, list and remove a secret

  1. Store a value

    The value is read from standard input and never from an argument, because arguments are visible to other users and end up in shell history. 

    printf '%s' 'postgres://shop:hunter2@db/shop' | kanea secret put shop/database-url

    The command prints wrote shop/database-url (31 bytes). Writing to an existing path replaces the value.

  2. Or store a file

    kanea secret put --from-file=./service-account.json shop/gcp-key

    A file is stored byte for byte. From standard input, one trailing newline is trimmed. A value may be up to 64 KiB.

  3. List what exists

    kanea secret ls shop

    The table shows each path, when it was created and updated, and its source. It never shows a value. Leave the project out to list every secret.

  4. Remove a secret

    kanea secret rm shop/gcp-key

    The command prints removed shop/gcp-key.

Paths are <project>/<name>, or shared/<name> for a secret every project may read. These commands work against a remote node too, with the client flags.

Reference a secret from a spec

Put the reference where the value would go:

env = {
  DATABASE_URL = "secret:shop/database-url"
}

Kanea writes the value to a file and sets the variable to the file's path. Two prefixes select how the value is delivered:

ReferenceThe variable holdsUse it when
secret:shop/database-urlThe path /run/kanea/secrets/<alloc>/shop/database-urlThe software can read a credential from a file. This is the default.
secret-env:shop/database-urlThe value itselfThe software only reads environment variables.

The file is mode 0400, owned by the user the service runs as, and mounted read-only at the same path inside the container. It lives on a tmpfs and goes away with the alloc.

The secret-env: form is weaker because an environment variable is readable through /proc/<pid>/environ and inherited by every child process. Both forms follow the same project scoping.

Other spec fields take a secret: reference as well, such as a storage credential or a registry credential. So do the credentials in the node config, for example auth.oidc.client_secret.

Sync secrets from an external provider

kanead can copy values from Doppler, HashiCorp Vault, AWS Secrets Manager, Azure Key Vault and Google Secret Manager into its own store. Specs do not change: they keep referencing secret:<project>/<name>.

Because the values land in the local store, the node keeps working through a provider outage on whatever the last sync wrote.

  1. Put the provider's credential in a file

    Credentials are files on the node, never values in the node config. The file must be readable by its owner only, or every mapping of that provider fails. 

    sudo install -d -m 0700 /etc/kanea/secrets
sudo install -m 0600 doppler.token /etc/kanea/secrets/doppler.token

  2. Add a provider block

    Edit /etc/kanea/kanea.hcl, the node config. The two labels are the provider kind and a name of your choosing. Each sync block maps one external value to one local path. 

    # /etc/kanea/kanea.hcl
provider "doppler" "main" {
  token_file = "/etc/kanea/secrets/doppler.token"
  project    = "shop"
  config     = "prd"
  allow      = ["shop"]

  sync {
    name = "DATABASE_URL"
    to   = "shop/database-url"
  }
  sync {
    name = "STRIPE_KEY"
    to   = "shop/stripe-key"
  }
}

  3. Restart kanead and check the sync

    sudo systemctl restart kanead
kanea secret providers

    The first pass runs at startup. The table lists each provider with its mapping count, the last attempt, the last success and a status of ok. A failing mapping gets its own row with the error.

  4. Confirm the secrets exist

    Run kanea secret ls shop. Synced secrets show doppler/main in the source column.

What every provider block needs

PartRule
First labelThe kind: doppler, vault, aws-sm, azure-kv or gcp-sm.
Second labelThe provider's name, a lowercase DNS label. It must be unique across all provider blocks.
allowRequired. The projects the block may write into. "shared" is also accepted.
syncAt least one. to is the local path and must sit in a project allow lists. Two sync blocks may not target the same path.
Credential filesAbsolute paths. A file that group or others can read is refused. One trailing newline is trimmed.
Endpoint overridesMust be http:// or https:// URLs. Plain HTTP is accepted with a warning, since it carries the provider's credential.
Attributes of another kindAn error. A vault block may not carry region, for example.

A malformed block stops kanead from starting, with a message that names the block and the problem.

HashiCorp Vault

Kanea reads KV version 2 secrets with a token. Other auth methods and secret engines are not supported. 

provider "vault" "infra" {
  address    = "https://vault.internal:8200"
  token_file = "/etc/kanea/secrets/vault.token"
  mount      = "kv"
  ca_file    = "/etc/kanea/tls/vault-ca.pem"
  allow      = ["shop", "shared"]

  sync {
    path  = "apps/shop"
    field = "session_key"
    to    = "shop/session-key"
  }
  sync {
    path  = "platform/smtp"
    field = "password"
    to    = "shared/smtp-password"
  }
}
AttributeTypeDefaultMeaning
addressstringrequiredThe Vault server's URL.
token_filestringrequiredFile holding a Vault token.
mountstringrequiredThe KV v2 mount.
ca_filestringsystem trust storePEM bundle for a private CA.
sync.pathstringrequiredThe secret's path under the mount.
sync.fieldstringrequiredOne key of that secret. Its value must be a string.

AWS Secrets Manager

Kanea signs requests with a static access key. Instance roles are not consulted. 

provider "aws-sm" "prod" {
  region          = "eu-central-1"
  access_key      = "AKIAEXAMPLE"
  secret_key_file = "/etc/kanea/secrets/aws.secret"
  allow           = ["shop"]

  sync {
    id       = "prod/shop/database"
    json_key = "password"
    to       = "shop/db-password"
  }
}

secret_key_filestringrequiredFile holding the secret access key.
endpointstringhttps://secretsmanager.<region>.amazonaws.comAPI endpoint.
sync.idstringrequiredThe secret's name or ARN.
sync.json_keystringthe whole valueOne string key of a JSON-object secret.
sync.version_stagestringAWSCURRENTThe version stage to read.

Azure Key Vault

Kanea authenticates as a service principal with a client secret. Managed identity is not consulted. 

provider "azure-kv" "corp" {
  vault_uri          = "https://kanea-prod.vault.azure.net"
  tenant_id          = "11111111-2222-3333-4444-555555555555"
  client_id          = "66666666-7777-8888-9999-000000000000"
  client_secret_file = "/etc/kanea/secrets/azure.secret"

Google Secret Manager

Kanea authenticates with a service-account key file. The metadata server is not consulted. 

provider "gcp-sm" "analytics" {
  credentials_file = "/etc/kanea/secrets/gcp-key.json"
  allow            = ["demo"]

  sync {
    name    = "warehouse-token"
    version = "3"
    to      = "demo/warehouse-token"
  }
}

When values are synced

kanead runs one pass at startup and then one every sync_interval. The default is five minutes and the floor is 30 seconds. Set it in the secrets stanza: 

secrets {
  sync_interval = "15m"
}
  • A value is written only when it differs from the stored one. An unchanged secret produces no write and no backup traffic.
  • One failing mapping does not stop the others. After a failed pass kanead retries after a minute, then backs off up to the interval.
  • A mapping always wins. If you overwrite a synced path with kanea secret put, the next pass puts the provider's value back and logs a warning.
  • Removing a sync block stops the syncing. The local secret stays until you remove it.
  • A pass that changes something emits secret.synced. A pass with failures emits secret.sync_failed.

A synced value reaches a running service the same way any rotation does: at the next replacement of its allocs.

What is re-read and what needs a restart

You changeWhat kanead does
The content of a credential file or a ca_fileNotices within a minute and runs a pass straight away. No restart. The check compares content, so a tool that writes and renames works.
A provider block, a sync mapping or secrets.sync_intervalNothing until you run sudo systemctl restart kanead. The blocks are read once, at startup.
A credential file into something unreadable or wrongFails that provider's mappings on each pass until the file is fixed. kanea secret providers shows the error.
A ca_file into something that does not loadKeeps the last working set of providers and logs the error once.
